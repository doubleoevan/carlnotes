## Context

The app already server-renders Markdown. `api/content.ts` reads the files under `content/blog/`,
renders them with `markdown-to-jsx` through `renderToStaticMarkup`, and wraps the result in a
coffee-toned `PAGE_STYLE` shared with the emails. `/feed.xml` in `api/pages.ts` builds its items from
those same pages and hands them to `toSiteFeedXml`, whose channel description already reads "Notes of
Carl: the blog, and what ships". Releases are the second half of that sentence, unwritten.

The docs site is the other candidate host and is the wrong one: Starlight builds to static files at
deploy time, and `api/seo.ts` already notes that it excludes the docs from the sitemap because they
are "statically built files instead of anything this route can read". A release published between
deploys would not appear until the next deploy.

Three constraints are settled before this design starts: the page renders on our own domain rather
than redirecting to GitHub; no pageview calls the GitHub API, whose unauthenticated limit is 60 per
hour per IP and therefore shared across every visitor; and the webhook acts only on
`action: "published"`.

## Goals / Non-Goals

**Goals:**
- One changelog, authored in GitHub Releases, read at `/releases`.
- A pageview that touches only our own database.
- A stored shape an email broadcast can read later without a schema change.
- A single idempotent path that both seeds history and repairs missed deliveries.

**Non-Goals:**
- Sending a release to subscribers. Deferred to its own change.
- Pagination. Every published release fits on the index for a long while yet.
- Rendering the `<details>` PR list on our page. The summary above `<!-- more -->` is the whole
of what we show.

## Decisions

### `/releases` is a top-level app route, not a Starlight page

The content changes when a release is published, which is not when the site is built. Starlight
cannot serve it without a deploy, and coupling "publish a release" to "redeploy the docs" reintroduces
the drift this change exists to remove. The route joins `api/pages.ts` beside `/blog`, reusing
`api/content.ts`'s renderer and page style so it reads as the same surface.

*Alternative considered:* a Starlight page regenerated by a scheduled build. Rejected — it adds a
build trigger, a delay between publish and visibility, and a second deploy path to keep working.

### The table stores markdown only; HTML is rendered per request

`api/content.ts` already renders per request, with the comment that a new page ships by adding a
file. Release volume is a handful of rows, so rendering is not a cost worth caching against.

Storing rendered HTML would create a second representation to invalidate whenever a release body is
edited on GitHub — and since the webhook deliberately ignores `edited`, that stored HTML would go
stale silently with nothing to correct it. Markdown-only also keeps the deferred email broadcast free:
an email needs its own inline-styled, table-based HTML, not the web page's markup, so storing web
HTML would serve neither reader well.

*Alternative considered:* store both, render once on upsert. Rejected — it buys nothing at this
volume and costs a consistency rule.

### The sync script is the repair path, not just the backfill

The script reads the GitHub releases API and upserts by tag, the same write the webhook performs.
Written that way it is one behavior with two uses: it seeds the releases that predate the webhook,
and re-running it reconciles anything a missed or failed delivery dropped. This is why it must be
idempotent and safe to re-run at any time, and it is the documented recovery step when `/releases`
is missing something GitHub shows.

Framing it as a one-time backfill instead would leave no answer to a dropped webhook other than
editing rows by hand.

*Alternative considered:* a scheduled poll that removes the need for a webhook. Rejected — it spends
API budget continuously to catch a rare miss, where the webhook is immediate and the script already
covers the gap on demand.

### Upsert by tag, filter on read

The tag is the natural key: GitHub guarantees one release per tag, and a re-delivered webhook must
land on the same row. `prerelease` is stored rather than filtered at write time, so a release that is
promoted from prerelease later needs no special handling — the read filters it, and the next upsert
or sync corrects the flag.

Drafts never arrive at all: an unpublished draft does not fire `published`, and the sync script skips
`draft: true`.

### Every release gets its own URL

The index at `/releases` is the browsing surface; `/releases/<tag>` is the addressable one. One page
carrying every release competes with itself: eight releases about eight different features share one
title, one canonical URL, and one set of terms to rank for. Separate pages each rank for what they are
actually about, and give anyone announcing a release something to link at that is not a GitHub tag.

It costs one route. The index shows summaries and links through; the tag page renders the body whole,
generated PR list included, since a reader who navigated to one release wants all of it.

*Alternative considered:* anchor links into the index. Rejected — an anchor is not a page, so it earns
no ranking of its own and shares the index's title in every preview card.

### The `<!-- more -->` split happens at render, not at write

The body is stored whole. The index splits on the sentinel and renders the part above it; the tag page
renders all of it; a body with no sentinel renders whole either way. Keeping the split at read time
means the stored row stays a faithful copy of what GitHub holds, which is what makes the sync script's
comparison meaningful and lets a future email choose a different cut.

## Risks / Trade-offs

- **A missed webhook leaves `/releases` silently behind GitHub.** → The sync script is the
documented repair, safe to re-run at any time. Worth adding a log line on upsert so a gap is
visible in the platform logs.
- **The signing secret is unset in an environment.** → The handler must reject every request when the
secret is missing rather than skipping verification. Failing closed on an unsigned webhook is the
whole point of signing it.
- **A release body written without the sentinel dumps the full PR list onto the page.** → Render the
whole body in that case, and document the convention in the repo. The failure is ugly, not broken.
- **Markdown from GitHub is author-written, not user-generated, but it is still HTML in a page.** →
It renders through the same `markdown-to-jsx` path the blog uses, which does not pass raw HTML
through. Release bodies come from repository maintainers, so this is a low-trust-boundary concern
rather than an open one.
- **The feed now needs the database, where it used to read files alone.** → `/feed.xml` logs a failed
release read and serves the blog items on their own. A feed reader is better served half a feed than a
500, and the failure is in the logs rather than swallowed. The pages themselves do not degrade: a
`/releases` request with no database is a real error and answers as one.
- **Screenshots in a release body must be absolute R2 urls.** → GitHub's own attachment urls are tied
to that release's rendering context; an R2 url serves the page today and the email later. This is a
convention the repo documents, not something the code can enforce.

## Migration Plan

1. Ship the table and the migration first — an empty table breaks nothing.
2. Ship the webhook handler and register it in the repository settings with the Doppler secret.
3. Run the sync script once to seed the releases that already exist.
4. Ship `/releases`, the sitemap entry, the feed items, and the `/changelog` redirect together, so
the page and everything pointing at it arrive at once.

Rollback is per-step: the route can be removed without touching the table, and the webhook can be
disabled in repository settings without a deploy.

## Open Questions

None blocking. The three the proposal was asked to resolve are decided above: `/releases` is a
top-level app route, the table stores markdown only, and the sync script is the repair path.
