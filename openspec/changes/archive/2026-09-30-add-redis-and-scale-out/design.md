## Context

The api is one Bun process behind Northflank's edge, and the worker is one process hosting three Temporal Workers. Four things keep the api and the worker at one copy each:

- **Sessions**: `api/api.ts` resolves the session on every `/api/*` request through Better Auth's Drizzle adapter, one Postgres read per request, anonymous ones included. The topic page reloads every three seconds while a scan runs (`ui/src/hooks/useTopicScan.ts`), and the badge poll runs every forty-five seconds per tab (`ui/src/components/chat/AppChatPanel.tsx`), and each of those requests runs that read.
- **Per-process maps**: `api/rateLimit.ts` counts tool callers in `hono-rate-limiter`'s memory store, `db/quotas.ts` counts suggestions in a `Map` cleared at the UTC day, `api/flagContent.ts` counts flags in a `Map` that never drops an entry, and `worker/schedule.ts` guards the sweep with an `isRunning` boolean. Each is right for one process and wrong for two.
- **Direct Neon connections**: `api/chat/roomStream.ts` and `api/note/noteStream.ts` each hold one `LISTEN` connection outside the connection pooler, built by `toDirectConnectionString`, the only reader of `DATABASE_URL_DIRECT`.
- **Worker arithmetic**: `MAX_CONCURRENT_SCAN_ACTIVITIES = 8` in `worker/temporal.ts` against the mean scan measured on production over the fourteen days to 2026-09-29, 244 seconds with a median of 230 over 115 scans, is a limit of about 2,800 scans a day. The plan was written against 165 seconds and 4,200 a day. The mean moved as the source mix changed. The sweep loads every topic row, filters in JS, resolves owners through an unbounded `Promise.all`, and re-reads each owner's quota per topic. `failStaleScans` measures from `startedAt`, which is set when the row opens, so queue time counts as run time. `resetMonthlyBudgets` runs one user at a time at the top of the sweep and matches every user with a LiteLLM key on the first of the month.

Measured on 2026-09-29 against two api processes of this change on the dev config, ports 3001 and 3002, with the compose Redis. A sign-in put the session and its active-sessions list in Redis, thirty-one MCP requests split across the two processes had the thirty-first rejected with 429 on whichever process it reached, a chat message posted through one process reached a stream held by the other with its tool calls, a note edit posted through one gave the other's stream a resync poke and its own stream the bytes, the mention count and a poll reload were cached in Redis, and an invite-access write showed on the other process's next session read. With Redis stopped, a sign-in, a session read, the mention count, and a rate-limited route all succeeded. The load test, `oha -z 10s -c 50` on `/api/topic-feed` signed in, served 269 requests in ten seconds, every one 200, with a median of 1.31 seconds and a 90th percentile of 2.86 seconds against the remote dev Neon. The pool queued during the burst, with 115 waiting at its end, and showed zero waiting once the burst drained. The request's query count is measured by Sentry in production only, so the session read's absence is verified from Better Auth's code path and the Redis keys, not counted in dev.

Constraints: Bun is pinned to 1.3.14, whose built-in `RedisClient` includes pub/sub, added in 1.2.23 and marked experimental, and needs Redis 7.2 or later. The Northflank addon is a single Redis node with Sentinel off and public access off, reached as `REDIS_URL`. Doppler prd maps it to the addon's `REDIS_MASTER_URL`, and Doppler dev sets it to `redis://localhost:6379`. Postgres is reached only through Neon's connection pooler in transaction mode. Temporal is one self-hosted server with no standby, and stays so. There is no staging environment. Replica counts, sizes, and cron schedules live in the Northflank UI, not the repo.

## Goals / Non-Goals

**Goals:**

- Every api request stops reading Postgres for its session, and a Redis outage costs latency, never a sign-out.
- Every limiter and counter the api holds is correct at any replica count, and every one fails open while Redis is down.
- Live updates fan out over Redis pub/sub with the delivery behavior they have today, and the api holds no connection outside the connection pooler.
- The api and the worker each run as N replicas with a stated rule for what N may be.
- The scan limit is a setting plus a replica count, sized from the measured scan duration, and the sweep, the reaper, and the reset stop being the parts that break first.

**Non-Goals:**

- Redis failover. One node is enough while sessions fall back to Postgres. Sentinel is a new addon later.
- Moving the note update bytes over Redis. The poke stays a poke.
- A separate scan-status route for the poll. The poll keeps reloading the topic page.
- Presence, cursors, or any change to what the streams send.
- Charging ingest spend to users, email retry, or Temporal redundancy. The Notion plan lists them. They are not this change.

## Decisions

### 1. One Redis module in `db/`, on Bun's built-in client, with fall-through as its contract

`db/redis.ts` owns the one command client, a `RedisClient` from `bun` built from `REDIS_URL`, and exports the operations its callers use, among them `runWithRedis(operation, runOperation)`, `cacheJson(key, ttlMs, load)`, `incrementRateLimitWindow(key, rateLimitWindowMs)`, and `readAndResetRedisGauges()`. `db/` is the home because `db/quotas.ts` needs the counter and `db/` is the module the api and the worker both import for stores. `shared/` reaches the network only for monitoring and analytics, and stays that way.

`runWithRedis` is the whole fall-through contract. It runs one operation, counts a failed one on the minute's gauges, logs the first failure of each minute, and returns `null` on any failure, including a client that is not connected. A call made while a reconnect waits fails at once without adding to the count, which the failed connect already raised. Every caller treats `null` as "Redis is unavailable" and does what it did before Redis existed. Nothing outside `db/redis.ts` touches the client directly. The client is built with `autoReconnect: false` and `enableOfflineQueue: false`, so a command against a dead connection rejects at once instead of queueing behind a reconnect and hanging a request. The module owns reconnection itself, on `onclose`, with the backoff the brokers use today, one second doubling to thirty, reset once a connect succeeds and, for the subscriber, once its subscribes succeed. Bun's own `autoReconnect` was rejected because it stops after `maxRetries` and would leave the process without Redis for good after a long outage.

`cacheJson` is read-through: `GET`, parse, return, else `load()` then `SET ... PX ttl`. On any Redis failure, or a stored value that does not parse, it calls `load()` and stores nothing. The parse runs inside `runWithRedis`, in `readRedisJson` too, so a value that does not parse is a failure like any other. `incrementRateLimitWindow` is one `EVAL` of a three-line script, `INCR`, `PEXPIRE` if the count is one, return the count and `PTTL`, so the window starts atomically with its first hit and the process dying between two commands can never leave an unexpiring key. It returns `{ count, resetAt }` or `null`. `decrementRateLimitWindow` is a one-line script that lowers a key only while it exists, so a refund that lands after its window expired never creates a key without an expiry.

Alternatives: `ioredis` was rejected because Bun's client covers `GET`/`SET`/`EVAL`/`PUBLISH`/`SUBSCRIBE` and adds no package. A Redis module per consumer was rejected because the fall-through rule and the reconnect loop must be written once.

### 2. Sessions in Redis with Postgres as the fallback, made explicit

`api/auth.ts` sets `secondaryStorage` to four functions over `runWithRedis`: `get` returns the value or `null`. `set` writes `SET key value EX ttl` if Better Auth passes a ttl, which it does for every session key, every active-sessions list, and every limiter key, and a plain `SET` otherwise. `delete` returns after logging a failure. `increment` runs `incrementRateLimitWindow` with the ttl Better Auth passes in seconds and returns the count, or 0 on `null`. It also sets `session.storeSessionInDatabase: true`. In the installed Better Auth (1.6.24) that combination does what the proposal asks, verified in `node_modules/better-auth/dist/db/internal-adapter.mjs`: `createSession` runs the database insert and then writes the session and the user's active-sessions list to secondary storage. `findSession` reads secondary storage first, and on a miss with `storeSessionInDatabase` set falls through to the database read. `deleteSession` and `deleteSessions` delete from both. So a Redis outage makes `get` return `null` and every request reads Postgres as it does today, and a Redis restart loses only the cache. The wrapper is what makes this explicit. Without it, a `get` that throws an error would propagate out of `getSession` and fail the request.

`api/auth.ts` also sets `verification.storeInDatabase: true`. With secondary storage configured, Better Auth otherwise keeps its verification values in Redis alone: reset and verification links, OAuth sign-in state, and MCP authorization codes. A Redis outage would then break every sign-in through Google or GitHub, and a restart would drop every link in flight. With the option set, Postgres stays their source of truth and Redis is read first, and `clearResetPasswordTokens` deletes a voided reset link's Redis copy along with its row.

Better Auth's rate limiter defaults its storage to `secondary-storage` the moment `secondaryStorage` is set (`create-context.mjs`), and builds its atomic `consume` on `increment` if the storage offers one. Without it, the limiter falls back to a read-modify-write and logs a best-effort warning at boot. The sign-in limiter therefore counts in Redis atomically and fails open with it, which is the stated behavior for every moved limiter.

Three things Better Auth does not do on its own, because the app writes the users row and closes accounts through Drizzle instead of through Better Auth's routes. Each gets one helper in a new `api/sessions.ts`, which writes the keys Better Auth owns directly through the store: a session under its raw token as `{ session, user }`, and the user's tokens in `active-sessions-<userId>` as `{ token, expiresAt }` entries. The helpers go through the store instead of through `auth.$context`'s internal adapter because the modules that write the users row are ones `api/auth.ts` imports, and could not import it back without a cycle.

- **The cached user goes stale.** A session's Redis entry holds the users row as it stood at sign-in, and `findSession` returns that snapshot without a Postgres read, where today every request joins the live row. `refreshSessionUser(userId)` reads the users row and the user's tokens from Postgres, so a token the list missed is refreshed too, and rewrites every session Redis still holds with the fresh row and its remaining ttl, the rewrite Better Auth's own `refreshUserSessions` makes after its update-user route. The rewrite is a `SET ... XX`, so a session a revocation deleted between the read and the write is never written back. It runs after each direct write to a field the session returns: the plan in `api/billing.ts`, the role in `api/admin.ts`, the username in `api/usernames.ts`, the avatar in `api/avatars.ts`, and the invite access in `api/users.ts`. The budget override and the LiteLLM key are not returned with the session, so their writes need nothing. Server-side authorization never read the session's copy and is unaffected.
- **A closed account stays signed in.** `deleteUser` in `api/users.ts` deletes the row, which cascades to the Postgres sessions and to nothing in Redis, so the cookie would keep resolving to the snapshot until its ttl. `revokeUserSessions(userId)` reads the user's tokens from Postgres, which keeps every session, and deletes them and the active-sessions list in one `DEL`, so a token the list missed goes too. It returns false if Redis is unreachable. `deleteUser` calls it first, and if `REDIS_URL` is set and Redis is unreachable, it deletes nothing and both close routes return 503 to try again. A Redis copy that outlived the row would keep the account signed in until its ttl. It calls it again just before the row delete, for a session cached while the close ran. The Stripe cancel and the LiteLLM key delete before it cannot run twice, so a Redis that stops answering by then is reported to Sentry and the close goes on. Without `REDIS_URL` there is nothing to sign out of, and the close goes on.
- **A session read from Postgres is never written back.** `findSession`'s fallback path writes nothing, and the daily refresh in `updateSession` skips its Redis write if the token is absent, so a session created before Redis, or during an outage, would read Postgres on every request until its user signed in again, and an active user's session, which each refresh extends, never expires. A `databaseHooks.session.update.after` hook, beside the `session.create.after` hook the app already has, receives the refreshed Postgres row and calls `cacheSession`, which, if the token is absent from Redis, writes `{ session, user }` under it with the remaining time and appends the token to the user's active-sessions list, the shape `createSession` writes. Every active session is therefore stored in Redis at its next daily refresh, and the first deploy and any restart repopulate within a day. A refresh whose Postgres update matched no row, because the session was revoked in Postgres alone, passes the hook no session. Better Auth rewrites the Redis copy with a later expiry before it updates Postgres, so without the hook's delete, that copy would outlive every refresh. The hook deletes the copy the request's signed session cookie names. Better Auth then throws a 401 error from `getSession`, which the session middleware in `api/api.ts` reads as signed out, so the request goes on without a user instead of failing.

Better Auth's own revocations have one gap of the same kind. Its active-sessions list is a JSON array updated by read-modify-write, so two sign-ins at once can drop a token from it, and `deleteUserSessions` on a password reset or change deletes only the listed tokens from Redis before it deletes every Postgres row. A `databaseHooks.session.delete.after` hook deletes each deleted row's token from Redis. Better Auth runs it once per deleted row, for a single delete and a bulk one alike (`deleteManyWithHooks` in `with-hooks.mjs`), so every revocation that reaches Postgres reaches Redis whether or not the list named the token.

### 3. Two responses cached, one of them only for polls

The mention count route wraps `countUnseenChatMentions` in `cacheJson("unseen-chat-mention-count:<userId>", 10 s)`. The badge polls every 45 seconds, so a count is never more than one poll stale. Opening a room saves its mentions as seen, and the team-chat spec says that clears every badge at once, so saving mentions as seen deletes the user's key after the write, which covers both mentions-seen routes. A mention arriving is allowed to be up to ten seconds late, inside the poll.

The scan poll is not a status route. `usePollWhileScanning` calls the page's `reloadTopicPage`, which fetches `GET /api/topics/:id`. That same function runs right after the user's own edits, so caching the topic page for everyone would serve a pre-edit page after a save. The poll therefore marks itself. The reload that `TopicScanButton` gives the hook passes an `isPoll` flag to `reloadTopicPage`, `fetchTopicPage` sends `?poll=1`, and only a poll response is served from `cacheJson("topic-page:<userId or visitor>:<topicId>", 2 s)`. Two seconds is under the fastest poll interval of three seconds, so a tab never reads the same cached page twice, and a second tab of the same user on the same topic shares one cached page. A user's edit is followed by an unflagged reload, which is never cached. For a single tab, this cache saves only the session read, which decision 2 already removes. It is kept because the proposal asks for it and it costs one flag, and a status route that lets the page reload only on change is the real fix, left out as a non-goal.

### 4. The three limiters become fixed windows in Redis, same keys, same numbers, fail open

- **The tool caller rate limit**: `hono-rate-limiter` takes a `store` with `increment(key)`, `decrement(key)`, and `resetKey(key)`. `api/rateLimit.ts` provides one over `incrementRateLimitWindow("rate-limit:<key>", 60 s)`, keeping `CALLER_RATE_LIMIT = 30`, the one-minute window, and `toRateLimitKey` untouched. A `null` from Redis returns `totalHits: 0`, so the request passes. The `standardHeaders` still read the store's numbers.
- **The daily suggestion counter**: `incrementDaySuggestionCount` calls `incrementRateLimitWindow("suggestions:<utcDay>:<userId>", 24 h)` and rejects past `DAILY_SUGGESTION_LIMIT = 300`. The UTC day in the key replaces the map's midnight reset, so a count never crosses a day. `null` allows the suggestion.
- **The flag counter**: `canFlag` calls `incrementRateLimitWindow("flags:<userId>", 24 h)` and rejects past `DAILY_FLAG_LIMIT = 10`. `refundFlag` is a `DECR`. Today the window starts at the user's first flag and lasts a day, and the Redis key expiring from its first hit is the same rolling day. `null` allows the flag.

All three maps are deleted. Failing open was chosen over failing closed because every one of these guards against spend or spam, none guards data, and a Redis outage should not turn the MCP server or the chat off.

### 5. Fan-out over Redis pub/sub through one subscriber connection per process

`db/redis.ts` also exports `publishToChannel(channel, payload)` and `subscribeToChannel(channel, onMessage)`. Subscribing takes over a Bun `RedisClient` connection, so the module holds one subscriber slot per process, filled lazily on the first `subscribe`. Each attempt to fill it, the first and every reconnect after a close, builds a fresh client, closes the dead one, connects, and subscribes every registered channel on the fresh client. Bun's client keeps its JavaScript listener registry across a drop while the server forgets the subscriptions, so subscribing again on the same client would run every handler twice after each reconnect. The reconnect is the same one-second-to-thirty backoff, reset once a subscribe succeeds, so the two brokers no longer each have a copy of that loop. A subscribe that fails on an open connection schedules the same reconnect, and the fresh client subscribes every channel, the failed one included. Two direct Neon connections per replica become two Redis connections per replica, the command client and the subscriber, which is the number to compare with the addon's client limit as replicas grow. An open subscription keeps a Bun process alive, confirmed on 1.3.14, where an open command connection does not. Only the api subscribes, so the sweep, the reset job, and the smoke scripts still exit on their own.

`api/chat/roomStream.ts` and `api/note/noteStream.ts` keep their emitters, their event keys, and their public functions, and both take the note broker's shape: emit to the process's own subscribers first, publish a payload that names the instance, and skip the echo of that instance's own publish. `notifyNoteUpdate` publishes `instanceId:noteId` as it does today. `notifyChatRoomMessage` emits the message id and its tool calls locally, then publishes `instanceId:topicId:teamId:messageId[:toolCalls]`, and the handler drops a payload whose instance id is its own. The chat broker today has neither the local emit nor the echo skip, and the proposal asked to keep that, but over Redis the two connections drop and reconnect independently. A publish on the storing instance can succeed while that instance's own subscriber is still in its backoff, and its streams would get nothing until the next message. Delivering locally first removes that dependence, and skipping its own echo keeps a tool call's toasts from arriving twice. `toDirectConnectionString` is deleted, and `DATABASE_URL_DIRECT` is removed from `.env.example`, `noteStream.test.ts`, and the README.

**The 7,000-byte limit goes.** It existed because `pg_notify` allows 8,000 bytes. Redis messages have no such limit, and the old one silently drops the toasts and the proposed-edit card that come with a tool call. **The note's poke-only payload stays.** A Yjs update can be megabytes after a paste, the resync path already exists and is exercised every fifteen minutes by the stream's age limit, and sending the update bytes would add a second delivery path to keep correct for no user-visible gain.

**Catch-up stays as it is.** Neither broker replays what a dropped connection missed. The chat stream loads everything past its cursor on the next message, and a note resyncs on the next poke or when the fifteen-minute age limit closes the stream. Redis pub/sub is fire-and-forget like `NOTIFY`, so nothing new is needed and nothing is added. A failed publish returns false and never fails the write that preceded it. It is reported the way any Redis failure is, in the minute line's counts and the store's one logged failure a minute, so an outage does not log a line for every chat message and note edit.

### 6. Replicas: the port from the environment, the instance on the minute line, and the state audit

`api/index.ts` drops `port: 3000` from its export. Bun reads `PORT` if the port is omitted, confirmed on 1.3.14, and defaults to 3000, so the Dockerfile's `EXPOSE 3000` and the Vite proxy's origin are unchanged. `shared/runtimeGauges.ts` adds `instance: hostname()` to the minute line, which on Northflank is the container's name, unique per replica.

Module-scope state that assumed one process, and what happens to each:

| State | Where | Verdict |
|---|---|---|
| Tool caller rate limit store | `api/rateLimit.ts` | Moves to Redis (decision 4) |
| Daily suggestion counts | `db/quotas.ts` | Moves to Redis (decision 4) |
| Flag counts | `api/flagContent.ts` | Moves to Redis (decision 4) |
| Better Auth sign-in limiter | inside Better Auth | Moves with `secondaryStorage` (decision 2) |
| Chat and note listeners | `api/chat/roomStream.ts`, `api/note/noteStream.ts` | Replaced by the shared subscriber (decision 5) |
| `topicSectionIdCache`, 60 s | `api/topic/feeds.ts` | Stays per process. A rank change clears one replica's copy. The others serve the old order for up to a minute, which the existing `ponytail:` comment already accepts, and a `cacheJson` swap is the one-line upgrade if that minute is ever noticed |
| `chatRoomDeltasByKey` | `api/chat/roomMessages.ts` | Stays. It dedupes concurrent loads inside one process. A second process loading the same delta is correct, only not shared |
| `pendingRenderByPreviewKey` | `api/share/preview.ts` | Stays. Same reason, and the rendered PNG is stored in object storage either way |
| `thresholdAlertSentAt` | `shared/monitoring.ts` | Stays per process. One condition may warn once an hour per replica. The fixed fingerprint groups them under one issue, so it is more events, not more issues |
| `htmlTimers`, `serverEditorPromise` | `api/note/notes.ts` | Stay. Each replica debounces the HTML it regenerates for the updates it merged, and a regeneration is idempotent |
| `hasCheckedTrustedProxies` | `api/auth.ts` | Stays. One report per replica boot is fine |
| Temporal `clientPromise`, analytics client, delay histogram | `worker/temporal-client.ts`, `shared/analytics.ts`, `shared/eventLoopDelay.ts` | Stay. Each is a per-process client or gauge by nature |

**The pool rule.** Every process opens up to `DATABASE_POOL_MAX` pooled connections, 40 by default. Neon's connection pooler accepts 10,000 client connections, but the server-side pool behind it for one user and database is 0.9 × `max_connections`, and `max_connections` follows the compute size: 112 at 0.25 CU, 225 at 0.5 CU, 450 at 1 CU, 901 at 2 CU. So the rule is `(api replicas + worker replicas) × DATABASE_POOL_MAX + one DATABASE_POOL_MAX each for the sweep and the reset ≤ 0.9 × max_connections`, counting both jobs because a sweep can still be running when the reset starts, and the jobs read the same setting as the services. One api and one worker with both jobs running are four pools, 160 at the default 40, which fits the 202 that 0.5 CU allows and not the 100 that 0.25 CU allows. Two api replicas and two worker replicas with both jobs are six pools, 240 at 40, which fits 1 CU (405) and not 0.5 CU, so at 0.5 CU every process sets `DATABASE_POOL_MAX=33`, 198 in all, and at 0.25 CU sets 16, 96 in all. The pool opens connections on demand, so this is the upper limit, and the minute line's `pool.totalCount` per instance is what to watch as replicas grow. The Neon compute size is read from the console before the count is raised. It does not live in the repo.

### 7. Scan concurrency is a setting, sized against the measured 244-second scan

`SCAN_CONCURRENCY` sets `maxConcurrentActivityTaskExecutions` on the scan Worker, default 8, read through `toPositiveInteger` from `db/index.ts`. Daily capacity is `worker replicas × SCAN_CONCURRENCY × 86,400 / mean scan seconds`, and the mean is 244 seconds, with a median of 230, over 115 scans in the fourteen days to 2026-09-29. With the free plan's one daily topic, a day's capacity is also about how many active free users the pipeline holds:

| Worker replicas | `SCAN_CONCURRENCY` | Scans a day at 244 s |
|---|---|---|
| 1 | 8 | 2,833, today's limit |
| 2 | 8 | 5,666 |
| 1 | 16 | 5,666 |
| 2 | 16 | 11,331 |
| 3 | 16 | 16,997 |

The numbers chosen: **two worker replicas at `SCAN_CONCURRENCY=8`** first, which doubles the limit to about 5,700 a day without changing what one process holds, and then **16 per replica**, about 11,300 a day, once the email change that limits digest sends is deployed. Each running scan also holds `REVIEW_CONCURRENCY` (4) fetches, so two replicas at 16 is 128 concurrent Firecrawl fetches against that plan's concurrency limit, and each finished scan sends one digest batch to Resend. At two replicas and 16 a scan finishes every eight seconds on average, but scans that finish together burst, which is what the email change bounds. After each raise, the worker's minute line should show a flat event loop delay, steady scan durations, and a quiet `scan-backlog` warning, and the mean is re-measured before any raise past 16, since it moved from 165 to 244 seconds in a month.

### 8. The sweep selects due topics in SQL, runs its owner reads eight at a time, and caches per sweep

The sweep's select becomes one query: topics left-joined to each topic's last completed scan start, `max(started_at) where topic_id = topics.id and status <> 'running'`, with the window filter in SQL. A topic is due with no completed scan, or with the last start older than a day for `daily` and `weekdays` and a week for `weekly`, and a `weekdays` topic that has been scanned is excluded on a UTC weekend. The `scans_topic_started_idx` index serves the subquery. `isTopicScheduled` goes, and its tests become tests of the query's rendered SQL through Drizzle's `toSQL()`, since `bun test` has no database. The tests check the rendered SQL and its parameters against the frequency and stale windows.

`loadDailyTopicIdsByOwner` runs its owners through `runWithConcurrency` at 8, the runner that `worker/review/score.ts` already has, moved to `worker/concurrency.ts` so the sweep and the reset can share it. The sweep caches each owner's remaining scan count in `remainingScanCountByOwner: Map<ownerId, number>`, read once per owner on first sight and decremented on each scan it starts, so an owner with ten due topics costs one quota read instead of ten. This map lives in the sweep instead of the request memo, because the memo clears on every write statement and the sweep writes constantly.

The sweep does not wait for the month's reset. A key created without a `budget_duration` keeps serving on the new month until its own budget is spent, so a topic that is due before the reset job has replaced its owner's key runs on last month's key as it does today, and a missing or failed reset run costs a late reset, never a day of scanning.

### 9. Staleness is measured from pickup, and a queued scan is closed out only past its ingest stage's total timeout

`scans` gains `picked_up_at`, nullable. `ingestForScan`, the first activity, records it where it is null, so the first attempt's start is the pickup and a retried ingest does not move it. `MAX_SCAN_DURATION_MS` already includes every retry. `failStaleScans` fails a scan on one of two predicates. A picked-up scan is stale if `picked_up_at` is older than `STALE_SCAN_MS`. A dispatched scan with no pickup is waiting for a slot and is left alone while its dispatch is younger than `INGEST_TOTAL_TIMEOUT_MS + FINISH_TOTAL_TIMEOUT_MS + STALE_SCAN_MARGIN_MS`, and stale once it is older. Temporal's schedule-to-close timeout counts queue time, so past the ingest stage's 90-minute total timeout the workflow has already failed the ingest without running it, its `failScan` activity has waited out its own 6-minute total timeout behind the same backlog, and the row would otherwise stay `running` for good with its dispatch marker set and no pickup, counted against the day's quota and skipped by the relay, the reaper, and the open-row read in `startTopicScan` alike. The topic page's own close-out uses the same filter. The queue is what alerts before either timeout. The `scan-backlog` threshold from the telemetry change already warns when the oldest waiting task passes fifteen minutes, on the worker's minute line and in the sweep, so a deep queue is a Sentry warning with the depth and age long before a scan is failed for waiting. `startedAt` keeps its meaning as the row's opening, which the due-ness rule and the quota count read.

### 10. The budget reset is its own job, four keys at a time, and the sweep no longer waits on it

`resetMonthlyBudgets` runs its due users through `runWithConcurrency` at 4, a limit the LiteLLM proxy handles easily, and keeps one attempt per user with failures reported. It moves out of the sweep into a new entry, `worker/resetMonthlyBudgets.ts`, run as `bun run reset:monthly-budgets` by a Northflank cron once a day shortly after midnight UTC, since a retry of a failed replacement has to happen more often than monthly and on the month's other days the query matches no one. The sweep's summary loses its reset line. The README's process table gets the job's row.

### 11. Both jobs take a database claim through the connection pooler

`db/claim.ts` exports `runWithClaim(claimName, task)`: one `db.transaction` that runs `select pg_try_advisory_xact_lock(hashtext(claimName))`, returns `null` without running the task if the lock is held elsewhere, and otherwise runs the task inside the transaction and returns its result. A transaction pins one pooled connection for its duration, which is exactly what makes a transaction-level lock work through Neon's transaction-mode connection pooler, and the lock releases with the transaction however the task ends, including a crashed process. The task's own queries run on `db`, on other pooled connections, and are not part of the claim's transaction. `toExclusiveTask` is deleted. The sweep claims `scheduled-scan-sweep` and the reset claims `monthly-budget-reset`. The Temporal worker needs no claim. Temporal hands each activity to one worker, so a second worker replica is safe on its own, and the claim is what makes a second sweep or reset invocation safe.

The advisory lock was chosen over a lease row because the codebase already takes `pg_advisory_xact_lock` for notes and rooms, it needs no table or migration, and it needs no expiry logic. Its limit is the transaction it holds open for the sweep's length, minutes today. A lease row with an expiry is the upgrade if that ever matters, and the code says so in a `ponytail:` comment.

## Risks / Trade-offs

- [Redis becomes a dependency of every request] → Every Redis call goes through `runWithRedis`, which returns `null` on failure, and every caller falls through: sessions to Postgres, caches to their loaders, limiters to allowing the request. Verified by running the dev api with `REDIS_URL` pointing at a closed port and exercising sign-in, the feed, a chat turn, and a suggestion.
- [A fail-open limiter is no limiter during an outage] → Accepted for a single-node Redis. The guarded paths cost model spend and spam, and the outage is visible on the api's minute line and as the `redis-down` warning.
- [Bun's Redis client and its pub/sub are marked experimental] → The brokers' contract is two functions, `publishToChannel` and `subscribeToChannel`, in one module. If the client misbehaves, `ioredis` replaces it behind those two functions and nothing outside `db/redis.ts` changes.
- [A Redis restart drops every subscription until the reconnect lands] → The reconnect resubscribes each channel, chat catches up from its cursor on the next message, and a note resyncs on the next poke or the fifteen-minute close, as with a dropped `LISTEN` today.
- [The poll cache serves a page up to two seconds old] → Only a poll reload is cached, an edit's reload is never cached, and two seconds is under the fastest poll.
- [A session cached in Redis outlives a revocation that only reached Postgres] → The delete hook deletes every deleted row's token from Redis, listed or not, and `deleteUser` revokes from the Postgres tokens, rejects the close while a configured Redis is unreachable, and revokes again just before the row delete. The remaining path is a hook's Redis delete that fails while Redis is unreachable during a sign-out or a password change, which the wrapper logs. That token then works until its next daily refresh, at most a day after its last one, when Better Auth's Postgres update matches no row, the refresh hook deletes its Redis copy, and the request is served signed out.
- [A Redis outage blocks account closes] → Accepted. A close during an outage returns 503 to try again and deletes nothing, where going on would leave a closed account signed in until its session's ttl.
- [Redis stops answering in the middle of a close] → The close finishes and the failed second revocation is reported, since its Stripe and LiteLLM steps cannot be retried. A session cached while the close ran then authenticates a user with no row until its next daily refresh finds no row and deletes its Redis copy, at most a day, and authorization reads Postgres, so it grants nothing.
- [The replicas' pools exceed Neon's server-side connections] → The pool rule in decision 6, checked against the compute size before each raise, and the `pool-waiting` warning already fires when a request queues.
- [Two replicas each warn once an hour] → Accepted: same issue, more events, and the instance on the line says which replica.
- [The claim's transaction stays open for the whole sweep] → Neon and PgBouncer set no idle-in-transaction timeout by default. If one is ever set, the sweep loses its claim mid-run and the next run could overlap. The lease-row upgrade is named in the code.
- [`hashtext` collides between two claim names, or with a note or room lock] → 32-bit hashes of two fixed strings. A collision between two jobs that never contend for anything would only make one of them skip a run, and the note and room locks hold for milliseconds.
- [The reset job is not configured, or a run fails] → Keys reset late and nothing else changes. An unreset key keeps serving until its budget is spent, the sweep scans on whatever key each owner holds, and the next daily run retries every failed replacement.
- [Raising `SCAN_CONCURRENCY` multiplies Firecrawl and Resend bursts] → The number is raised after the email change lands, one step at a time, watching the worker's minute line and the scan failure rate.
- [Temporal is one self-hosted server with no standby] → Accepted. A Temporal outage stops every scan, attachment job, and source screening until it is back, and no worker replica count changes that. The api keeps serving, a scan the sweep cannot start counts as failed and its topic stays due for the next sweep, and a row opened at topic creation waits undispatched for the relay. Making Temporal redundant is a separate decision, not part of this change.
- [Northflank's Redis version is below 7.2] → Bun's client rejects older servers. The addon's version is checked before `REDIS_URL` is set. The fallback keeps the app up while it is fixed.

## Migration Plan

1. Land the code with `REDIS_URL` set in Doppler dev to the compose Redis and in prd to the addon's master url, `SCAN_CONCURRENCY` unset, one replica of each service. Everything falls through if Redis is missing, so the deploy is safe before the addon exists.
2. Run the migration that adds `scans.picked_up_at` with the deploy job, as every migration runs.
3. Right after the deploy, add the `reset:monthly-budgets` cron in Northflank, a job on the new image that runs daily at 00:05 UTC, before the first of the next month. The job needs the new code, and the old sweep resets budgets until the deploy. Until it exists, keys stop resetting, which is the one thing this change breaks if the step is skipped.
4. Watch the api's minute line for `redis.isConnected` and the hit counts, then raise the api to two replicas after checking the Neon compute size against the pool rule. Run the 35.2 `oha` test against the app's `code.run` url before and after.
5. Raise the worker to two replicas at `SCAN_CONCURRENCY=8`, about 5,700 scans a day, after checking the compute size against the pool rule for six pools. Set `SCAN_CONCURRENCY=16` on each, about 11,300 a day, only after the email change lands.
6. Rollback is one replica per service and the previous image. `REDIS_URL` can stay set. The previous image never reads it. Sessions written under this change also exist in Postgres, so a rollback signs nobody out.
