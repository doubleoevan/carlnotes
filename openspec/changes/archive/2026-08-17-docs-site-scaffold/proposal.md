## Why

The docs surface is three markdown files rendered by the same 160-line handler that serves the blog, with no sidebar, no navigation, no search, and no room to grow into the eight-page manual the product needs. A documentation site is a solved problem, and Astro Starlight solves it — sidebar, mobile nav, dark mode, and Pagefind search with no search infrastructure to run. This change stands the site up and hands it `/docs`, without writing page content yet, so the writing lands on finished scaffolding instead of blocking on it.

## What Changes

- Add an Astro Starlight project at `docs/`, configured with site `https://carlnotes.com`, base `/docs`, and `outDir ./dist`, built by a new `build:docs` script.
- Mount the built static output in Hono under `/docs` via `serveStatic`, rewriting the request path to strip the `/docs` prefix, ahead of the SPA fallback so a docs path never resolves to the app shell.
- Define the sidebar as four sections in order — Start here, Topics, Your topic feed, Account — each autogenerated from its own subdirectory, page order coming from `sidebar.order` in frontmatter.
- Establish `docs/src/assets/screenshots/` as the home for screenshots, referenced relatively and never from `public/`.
- Write the docs as eight pages across the four sections, replacing the three essays the previous `content/docs/` surface published. Those three urls redirect to the docs landing page, so no inbound link breaks.
- Create the remaining page files as stubs excluded from the production build, so the sidebar is not padded with empty entries.
- **BREAKING** Remove the `docs` surface from `api/content.ts` and delete `content/docs/`. The `/docs` and `/docs/:slug` routes are answered by Starlight instead of the markdown renderer, and their JSON-LD `Article` tags go away with them.
- Drop `/docs` and its pages from the generated `sitemap.xml`; ours keeps the app routes and the blog, and Starlight emits its own docs sitemap.
- Build the docs in the Dockerfile build stage and copy the output into the runtime image, so the static site ships with the app service.

## Capabilities

### New Capabilities
- `docs-site`: the Starlight documentation site — its structure, sidebar, screenshot convention, build script, static mount under `/docs`, and inclusion in the deployed image.

### Modified Capabilities
- `blog`: the server-rendered markdown surface narrows from two surfaces to one. Only `/blog` remains; the docs half of the requirement is removed.
- `seo`: the sitemap requirement drops the docs pages, since Starlight emits the docs sitemap.
- `static-serving`: `/docs` is claimed by the docs static handler ahead of the SPA fallback, so an unknown docs path answers a docs 404 rather than the app shell.

## Impact

- **New**: `docs/` (Astro Starlight project, its own `astro.config.mjs`, content collection, and stub pages), `build:docs` script in the root `package.json`.
- **Modified**: `api/content.ts` (drop the `docs` surface and its routes), `api/pages.ts` (drop docs paths from the sitemap), `api/index.ts` (mount the docs static handler), `Dockerfile` (build docs, copy `docs/dist`, stop copying `content/docs`), `README` Development section (the new script).
- **Deleted**: `content/docs/` — its three pages move into `docs/src/content/docs/`.
- **Dependencies**: `astro` and `@astrojs/starlight` as dev dependencies. Astro runs on Node under Bun's package manager; the docs build is a build-time toolchain, so nothing new reaches the runtime image beyond the static output.
- **Not affected**: the blog keeps its markdown pipeline, frontmatter shape, JSON-LD, and canonical handling unchanged.

## Out of Scope

Tracked separately: writing the eight documentation pages, capturing screenshots, the blog RSS feed at `/blog/rss.xml`, the theme-aware content shell, and the Privacy and Terms migration out of the SPA.
