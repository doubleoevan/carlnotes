## ADDED Requirements

### Requirement: The documentation site is a Starlight project built to static files

The documentation SHALL be an Astro Starlight project at `docs/`, configured with `site` set to the production origin, `base` set to `/docs`, and `outDir` set to `./dist`. It SHALL be built by a `build:docs` script in the root `package.json`, which produces static HTML, CSS, and assets under `docs/dist` and requires no running process of its own.

Astro and Starlight SHALL be dev dependencies. They run only at build time, so no new package reaches the production runtime.

#### Scenario: The build produces a static site

- **WHEN** `bun run build:docs` runs
- **THEN** `docs/dist` holds the built HTML, assets, and search index, and no server process is started

#### Scenario: The site option is set so emitted URLs are absolute

- **WHEN** Starlight emits its sitemap and canonical URLs
- **THEN** each URL is absolute against the production origin, not a relative path

### Requirement: The app server serves the built docs under /docs

The app service SHALL serve `docs/dist` under `/docs` through Hono's Bun `serveStatic`, from the same process that serves the API and the UI bundle. Because Astro's `base` prefixes generated links without nesting the build output, the handler SHALL rewrite the incoming request path to strip the `/docs` prefix before resolving a file.

The docs handler SHALL sit ahead of the UI bundle's static handler and the SPA fallback, so no `/docs` path is answered with the app shell.

#### Scenario: A docs page is served

- **WHEN** a reader opens `/docs/how-carlnotes-works/`
- **THEN** the app answers 200 with that page's built HTML from `docs/dist`

#### Scenario: A docs asset is served

- **WHEN** a request arrives for a built docs asset under `/docs/_astro/`
- **THEN** the app answers 200 with that file's bytes, the `/docs` prefix having been stripped to resolve it

#### Scenario: A docs path never falls through to the app shell

- **WHEN** a request arrives for a path under `/docs`
- **THEN** it is answered by the docs handler, and never by the SPA fallback's `index.html`

### Requirement: Directory URLs resolve to their index page

The docs SHALL be built with Astro's directory output format, so each page is written as `<slug>/index.html`, and with trailing slashes always generated on internal links.

A request for a docs path carrying no file extension SHALL resolve to that path's `index.html`, whether or not the request ends in a slash. A path that does carry a file extension SHALL be resolved as the file it names.

A docs path matching no built file SHALL be answered with the docs site's own `404.html`, not the app shell.

#### Scenario: A page URL without a trailing slash resolves

- **WHEN** a reader opens `/docs/how-carlnotes-works` with no trailing slash
- **THEN** the app answers 200 with that page, rather than 404ing or falling through to the app shell

#### Scenario: A page URL with a trailing slash resolves

- **WHEN** a reader opens `/docs/how-carlnotes-works/`
- **THEN** the app answers 200 with the same page

#### Scenario: The docs index resolves

- **WHEN** a reader opens `/docs`
- **THEN** the app answers 200 with the docs home page

#### Scenario: An unknown docs path is a docs 404

- **WHEN** a request arrives for a `/docs` path matching no built file
- **THEN** the app answers with the docs site's 404 page, and never with the app shell

### Requirement: The sidebar is four sections, autogenerated and ordered by frontmatter

The sidebar SHALL list four sections in this order: Start here, Topics, Your topic feed, Account. Topics, Your topic feed, and Account SHALL each be autogenerated from their own subdirectory under the docs content directory, so adding a page there adds a sidebar entry with no configuration change.

Start here SHALL name its two pages explicitly, because they sit at the content root: the landing page a reader reaches at `/docs`, and the quickstart one segment below it. Keeping them out of a subdirectory keeps those two urls short, which is worth naming two pages in configuration.

A page's position within an autogenerated section SHALL come from `sidebar.order` in that page's frontmatter.

#### Scenario: The sections appear in the configured order

- **WHEN** a reader opens any docs page
- **THEN** the sidebar shows Start here, Topics, Your topic feed, and Account in that order

#### Scenario: A new page appears without configuration

- **WHEN** a markdown file is added to a section's subdirectory
- **THEN** it appears in that section's sidebar with no edit to the site configuration

#### Scenario: Frontmatter sets the page order

- **WHEN** two pages in one section declare different `sidebar.order` values
- **THEN** the lower value is listed first

#### Scenario: Start here lists its two pages

- **WHEN** a reader opens any docs page
- **THEN** Start here lists the landing page and the quickstart, in that order

### Requirement: The urls the previous docs surface published still answer

The markdown renderer that served `/docs` before this change published three pages, and the docs written here replaced them. Each of those three urls SHALL still answer and send the reader to the docs landing page, so an inbound link or a search result does not reach a dead end. Each SHALL declare the landing page as its canonical url and ask crawlers not to index it, so the retired url does not compete with the page that replaced it.

#### Scenario: A retired url reaches the docs

- **WHEN** a reader opens one of the three urls the previous docs surface published
- **THEN** the response sends them to the docs landing page rather than answering 404

#### Scenario: A retired url does not compete in search

- **WHEN** a crawler fetches one of those urls
- **THEN** it reads a canonical url pointing at the landing page, and a directive not to index the retired url

### Requirement: An unwritten page is a draft excluded from the production build

A page that exists as structure but carries no content yet SHALL be marked as a draft in frontmatter, so that the production build excludes it and the published sidebar lists only pages a reader can use. A draft SHALL remain visible when the docs run in development, so the full tree can be reviewed.

#### Scenario: A draft is not published

- **WHEN** the docs are built for production
- **THEN** no draft page is emitted and no draft appears in the sidebar

#### Scenario: A draft is visible while developing

- **WHEN** the docs run in development
- **THEN** every draft page and its sidebar entry are visible

### Requirement: Screenshots are project assets referenced relatively

Screenshots SHALL live under `docs/src/assets/screenshots/` and SHALL be referenced by relative path from the page that uses them. A screenshot SHALL NOT be served from the docs `public/` directory or referenced by an absolute path.

Astro applies the base path to images it processes and does not apply it to absolute paths written by hand, so an absolute reference resolves in development and 404s in production. Referencing assets relatively keeps the base path correct in both.

#### Scenario: A screenshot resolves in the deployed site

- **WHEN** a page referencing a screenshot is served under `/docs`
- **THEN** the image loads, its URL carrying the `/docs` base prefix

#### Scenario: Screenshots are not served from public

- **WHEN** the docs project is inspected
- **THEN** no screenshot is stored in its `public/` directory

### Requirement: Docs search ships with the site

The docs SHALL provide full-text search over their own pages, served as static files built alongside the site and requiring no search service to run.

#### Scenario: A reader searches the docs

- **WHEN** a reader searches from a docs page
- **THEN** matching docs pages are returned from the static index built with the site

### Requirement: The deployed image carries the built docs

The app image SHALL build the docs in its build stage and copy the built output into its runtime stage, so the static docs ship with the app service on the same deploy as the rest of the app.

#### Scenario: The image serves docs

- **WHEN** the built image starts and a request arrives for a docs page
- **THEN** the page is served from the docs output carried in the image

#### Scenario: The docs toolchain stays out of the runtime

- **WHEN** the runtime stage is built
- **THEN** it carries the built docs output, and neither Astro nor Starlight is installed in it
