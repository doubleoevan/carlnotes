# Design

## Context

See `proposal.md` for motivation and scope. The user approved implementation by invoking `$openspec-apply-change` on November 2, 2026.

The [CarlNotes workflow](https://app.notion.com/p/40462400378d8120bddcfd51302e49b7) was read on November 2, 2026; its last edit was October 25. It treats personal material as context and outside-world links as Resources. Its connection nudge, connected-AI Agent picker, and suggestions based on repeated matches belong in this change. Enterprise learning remains excluded; the user now explicitly includes sender-private annotations.

Observed implementation constraints:

| Existing implementation | Consequence |
| --- | --- |
| `packages/pipeline/ingest/index.ts` dispatches ready Sources and globally deduplicates Resources | New ingesters must keep private titles, summaries, senders, and chat links out of Resource columns. |
| `packages/pipeline/attach.ts` builds context for both review and `ingest/search.ts` | Adding Personal sources text unconditionally would send derived private details into Exa queries. |
| Attachment uploads accept 10 MiB; attachment context allows 20,000 characters | Reuse the upload constant. Bound Personal sources context separately inside existing review limits. |
| `review/filter.ts` caps topic context at 24,000 characters | Reserve space for Personal sources context without raising the scoring context ceiling. Update spend estimates to reflect the actual bound. |
| `apps/api/chat/encryption.ts` implements `enc1:` AES-256-GCM, with a keyless-development plaintext fallback | Extract reusable encryption below the apps; Personal sources persistence must require a key even in development. Preserve chat compatibility. |
| `toolCaller.ts` verifies `azp` but returns only a client display name | Preserve verified client ID. Resolve connection state from OAuth rows before each send. |
| `oauth_refresh_tokens` records expiry, revocation, rotation, user, client, and resource | A still-valid JWT is insufficient evidence of an active send connection. |
| `saveTopic.ts` deletes Sources omitted by a form | Personal sources need explicit deletion and preservation across stale saves. |
| Topic access includes owning and holding Teams; admin overrides exist | `visibility = private` alone cannot enforce sender-only Personal sources. |
| Fetched Sources have a ten-row limit; mobile response enums are frozen | Receiving Sources are excluded from the limit, and new kinds use an additive compatibility path. |
| MCP specs enumerate eleven tools, seven destructive account tools, and five MCP view tools | Add send and routing tools for thirteen total, with a separate additive-write annotation class. Keep the existing seven conservative hints. |

## Goals / Non-Goals

**Goals:** one received-content lifecycle; predictable retries; sender-only content and derived output; bounded asynchronous summarization; shared behavior across web, native apps, and MCP.

**Non-Goals:** mailbox access, conversation-history access through MCP, arbitrary webhook URLs, scoring inside ingesters, global learning from private text, or a general-purpose import platform. This proposal does not change deployment topology or the active `split-web-from-api` change.

## Decisions

### 1. Approval decisions

The user approved all seven recommendations below through the apply request on November 2, 2026. The later naming, mockup, and November 3 shared-address, editable-Topic, and sender-private annotation revisions supersede the original UI and email decisions. The November 3 final additions extend explicit routing language, move summarization billing to each Topic owner, configure receiving addresses by environment, and require replies for authenticated filing refusals. The user explicitly confirmed that stored items and summaries, as well as annotations, are visible only to their sender, even to the Topic owner. The approval covers implementation; production provisioning and rollout remain separate operational steps.

| Decision | Recommendation | Reason and alternative |
| --- | --- | --- |
| Source kinds | Stored `ai_agent`, `email`; identifiers `aiAgent`; copy “AI Agent”, “Email” | Matches `chat_room`. Reject `aiAgent` as a stored enum and a third kind for imports. |
| Received record | **Personal Source Entry**, `PersonalSourceEntry`, `personal_source_entries` | Covers sends, mail, and imports without colliding with Note, Chat Turn, Resource, or Finding. Use Entry in domain identifiers; the mockups use item in customer copy. |
| Email routing | Write or forward to the same address Carl sends digests from. File every clear editable match together. | Confirm with linked Topics in the same thread. Ask for numbers or existing Topic names when the match is unclear. |
| API key | `cnk_v1_<public-id>_<43-character base64url secret>`; 32 random secret bytes; SHA-256 digest only | A random bearer secret needs no reversible storage. Public ID supports indexed lookup and redacted display. Password-style slow hashing adds little for 256-bit random secrets. |
| Email entitlement and shared cap | Plus and Premium include forwarding; Free does not. AI Agent sends and accepted emails share one 200-per-day ceiling on every plan per UTC day. | One accepted message consumes one allowance regardless of transport or destination count. Imports and refusals consume none. |
| Later sharing | Keep ordinary Topic edit, visibility, Team, and ownership rules | Sender-owned private data is isolated from Topic-visible data; no activation lock is required. |
| Finding and podcast output | Write page-grounded public explanation and sender-private annotations together; narrate only public explanation | One structured call per sender supplies both layers. Separate encrypted annotation storage and authorized reads prevent visibility changes from exposing private text. |

Use **Personal sources** for the feature and **Personal Source Entry** / `PersonalSourceEntry` / `personal_source_entries` for a received record. Migrate the domain vocabulary, code identifiers, paths, routes, scripts, and docs together. Use data-preserving migrations for already applied development tables, retain decryptability and retry identity, and reconcile in-flight jobs before changing their names. Keep the configured receiving hostname and webhook. Only the environment’s shared mailbox accepts new mail. Add both Source kinds to the domain skill before introducing their identifiers in code. Add `ai` to code-style's abbreviation exceptions. Keep “scan” in identifiers and OpenSpec; use “brew” only in proposed customer copy.

### 2. Sender-owned storage and privacy

Keep encrypted `personal_source_entries` keyed to Source, Topic, and sender account, independent of the Topic owner. Scope each receiving Source to `(topic, sender, concrete AI Agent identity)` or `(topic, sender, email)`. Use one context row per `(topic, sender)`, with independent revisions and bounded text. Charge summarization to the destination Topic owner’s budget without changing the summary’s sender-only ownership. Existing rows retain their original sender and ciphertext. A single Topic workflow may process pending sender contexts sequentially; workflow arguments/history continue carrying IDs and counts only.

Every item, title page, count, Source group, link outcome, summary, and private annotation query filters by the authenticated sender ID before decryption. Topic owners, Team leaders, followers, and administrators cannot read another sender's private content. The shared section appears for every user with their own retained items who can still view the Topic, regardless of ownership or current edit permission. Topics with no live sender items hide this section; receiving setup stays in the Topic editor and account controls. It shows only that person’s counts. Removed edit permission stops new contributions and excludes that sender's context from future scoring; retained personal data can still be deleted by its sender. Topic/account deletion cascades private content. Old clients still preserve hidden receiving Sources.

Store annotations separately from Findings, keyed by `(finding, sender)` with encrypted text and the source-context revision. A private endpoint checks the viewer is that sender and can see the Finding; it never adds annotations to shared feed payloads, public caches, SSR, exports, emails, cards, chat retrieval, or podcast inputs. Deleting a source item invalidates its dependent annotations and pending generated text. The public Finding remains. Outbound reply snapshots cascade with their item/account while content-free delivery retry records remain.

### 3. Editable Topics and visibility

Accept sends, imports, and authenticated email wherever the central `topic:edit` gate permits the sender, including private, invite, public, and owning-Team Topics. Being a follower or a member of a holding Team alone does not grant edit permission. Admin edit authority permits contributing their own context, never reading somebody else's. Recheck edit permission in acceptance and before using context during review. The shared send allowance and email entitlement remain sender-owned. Email requires Plus or Premium; API keys retain their existing Premium gate.

Remove Personal sources activation checks from visibility changes, invitations, Team assignment/sharing, ownership transfer, and podcast generation. Keep ordinary authorization and Source reconciliation. A visibility change changes access to Topic-visible content only; it cannot broaden private item, summary, or annotation access. Do not re-enable podcast switches the user has manually disabled. Preserve historical user data while converting any explanations generated by the prior private-only implementation (migration below).

### 4. Source configuration and editor reconciliation

Use one `ai_agent` Source per Topic and concrete delivery identity. Configuration is a discriminated union:

- OAuth: `{ delivery: "oauth", clientId, appDomain }`.
- API: `{ delivery: "api_key", apiKeyId }`, displayed with the owner's key label, never as an authenticated Claude or ChatGPT identity.
- Import: `{ delivery: "import", provider: "chatgpt" | "claude" | "transcript" }`.

Imports and API sends do not manufacture OAuth client IDs. Group OAuth registrations by app domain in account controls and Topic presentation, while preserving each Source's actual client ID. A known app label comes from a maintained domain mapping. Unknown domains display as domains. Loopback/custom-scheme-only clients remain identified by client ID and display as local clients; never group unrelated clients under `localhost`.

Each sender has at most one email Source per Topic, created by the first accepted message. The shared address is public environment configuration. Sender authentication and Topic edit permission grant receiving authority. A valid account sender and current Topic edit authority are required at persistence.

Personal sources are immediately ready after validation and fetch nothing, so they do not count toward `MAX_TOPIC_SOURCES`. Show them in the editor outside the fetched count. Use a uniqueness constraint for each concrete identity. First sends, imports, and accepted email succeed at ten fetched Sources if otherwise authorized. Fetched creation and reconciliation count only rows without a Personal sources identity under the Topic lock; an eleventh fetched Source is still refused.

Generic topic saves preserve all Personal sources unless an explicit Personal sources removal action names one. Preserve fetched-Source reconciliation. Deletion uses its own endpoint, confirmation, cascades, and context invalidation. Concurrent first sends, imports, and form saves retain exactly one Source per identity.

### 5. Connected AI Agents and revocation

Return verified `clientId` alongside user identity from `resolveToolCaller`. Do not derive identity from User-AI Agent, request arguments, or `oauth_clients.name`.

For each send, require a non-disabled client, the user's current consent for MCP, and an unrevoked, unrotated refresh token whose expiry is in the future. A null expiry is live only where the auth provider explicitly treats it as non-expiring. Check resource binding and user/client linkage. Revocation and acceptance serialize on the same user/client grant lock, so a send admitted after revocation cannot slip through.

Derive app domain from a validated HTTPS client-metadata-document ID, otherwise an unambiguous registered HTTPS redirect host. Preserve exact normalized hosts; use explicit aliases for recognized multi-domain apps. Domain labels describe registration, not a vendor certification. Do not trust a self-reported app name or claim loopback redirects prove a vendor identity.

The account query joins clients, consents, and refresh-token state. Source history supplies a disconnected row if grant rows have been removed. No AI Agent-connection table is added. Revoke all of the user's grants in the selected app group, without affecting another user's grants or globally disabling the client. New sends stop immediately through the live-grant check; existing JWT reads retain their documented expiry behavior. Previously accepted entries remain encrypted until explicit deletion.

Show a dismissible connection nudge once per new grant, keyed by consent creation; keep dismissal in existing account preferences. Offer one-tap connected-AI Agent additions on eligible Topics. Suggest a connected app for an eligible Topic when at least three already accepted sends from that app match its existing Topic description within 30 days. Compute this from authorized existing entries without saving new profiles or routing counters. A suggestion never sends or creates a Source automatically.

Match accepted titles and summaries locally against normalized whole words in the current description, excluding common filler words. Require half those words, with at least two when available. Group matches across the app's live concrete registrations. Read ciphertext in pages of 100, decrypt one entry at a time, and return only app identities. Deleted, imported, email, and API-key entries do not count. This setup hint makes no model call and stores no search index.

### 6. One send service, MCP and API adapters

Define a shared request contract: one to twenty distinct `topic_ids` (or legacy `topic_id` for one), title of 1–200 characters, summary of 1–2,000 Unicode code points, at most ten distinct HTTP(S) links, optional HTTP(S) conversation reference or strict existing-chat Codex `chat_url`, and optional `request_id` for retry safety. Reject oversize input rather than silently truncating a send. Normalize canonical URLs, reject credentials/non-public hosts, strip recognized tracking parameters, and keep the chat URL outside the candidate list.

After transport/payload validation, check sender identity, daily allowance, then Topic edit access, in that order. Commit one sender quota charge with the atomic delivery, storing one independent item per destination Topic. Deleting one destination’s item neither removes the others nor refunds the charge. Use one logical per-user UTC-day allowance across AI Agent sends, API sends, and accepted emails. Keep the existing per-origin daily rows for attribution, but every read and acceptance check sums send and email counts under the existing account lock. Increment only the accepted delivery’s origin row in the same transaction. This reuses the current schema while preventing two transports from spending the last slot. Entitlement is separate: email requires Plus or Premium, while all enabled origins use one shared 200-per-day constant. This runaway-AI Agent safeguard applies to every account, including admins; entitlement overrides do not bypass it. The allowance check recognizes a previously accepted retry ID without demanding fresh quota; current identity and Topic access still apply. A retry with the same sender/request ID returns the original confirmation; different content under that ID conflicts. Store only a keyed payload digest in retry metadata. Deleted content cannot be recreated by replaying its ID.

When the user explicitly asks to send, share, save, add, or forward something to Carl, CarlNotes, or their topics without naming a Topic, call `suggest_topics`, then wait for their choice before sending. A named Topic goes directly to `send_to_topic` after resolving its ID; an ambiguous name needs clarification, not an inferred destination. Never initiate either tool without the user’s request.

`suggest_topics` on both MCP routes takes the same bounded title, summary, and public links, plus an optional editable-name `query` and the `list_topics` cursor. It stores no content, draft, Source, entry, counter, or vector and consumes no send or draft allowance. Both routes return every editable Topic, with the strongest content matches first and recommended. The send picker omits public discovery. A bound connection must switch to `/mcp` to act on another Topic.

Use the requesting sender's already provisioned model key to embed supplied content and current Topic names, prompts, and ready attachment context. Process the whole eligible catalog in keyset batches of 64; embeddings remain transient and private telemetry is suppressed. Stable text avoids random delimiter changes between cursor pages. Reuse identical input vectors within each batch. Recheck edit authority and matched context before returning results. Missing keys, changed matched context, or provider failures return unavailable without provisioning or logging private input. Strong recommendations require cosine similarity strictly above 0.6. Keep weaker editable Topics unchecked. Sort by score then Topic ID and return five Topics per page within the existing 40,000-character budget and opaque `list_topics` offset cursor. Email still requires clear relevance before filing. Repeated pages carry the same content; concurrent Topic changes have the same offset-pagination limitations as `list_topics`.

Every page and search offers a new private Topic, without generating or saving a draft. When the user picks it, use the existing `suggest_sources` daily allowance and Topic Draft schema. `create_topic` first returns that draft and an account/client/draft-bound confirmation expiring in 15 minutes. Only after the user confirms may a repeat call invoke `createTopicFromDraft`, preserving its plan, Source, moderation, and creation gates. A newly drafted Topic defaults private and retains ordinary Topic Draft controls and podcast settings. Creation never sends the original content automatically.

Expose `send_to_topic` on both MCP routes. Both routes require explicit destinations; the bound route refuses any different ID. Visitors receive the existing connect-account tool result. Disconnected users receive reconnect guidance. Success names the accepted title, Topic, entry ID, and distinct queued-link count, with the same information in text, structured content, and the topic MCP view. Do not return the private transcript, other entries, or chat link through the MCP view.

Use a title, `readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: false` without a mandatory retry key, and accurate open-world metadata. The tool only adds an entry; it never replaces existing entries or starts a Scan. Say to use it only for a summary the user explicitly asks to save, including an explicit scheduled instruction. A good send summarizes what the user is working on or asking about, conclusions, open questions, and the links that mattered. Never paste raw conversations. Its description and API setup docs explain editable destinations and the separation between public explanations and sender-private material before first use. Never instruct an assistant to inspect history, memory, files, or conversation summaries.

Serve the equivalent request at `POST /api/personal-sources/sends`, authenticated only by `Authorization: Bearer <API key>`. It has no account-wide read powers. CORS stays closed to arbitrary origins. Missing/invalid/revoked credentials return 401, exhausted daily caps 429 with reset time, hidden Topics 404, and unsuitable owned Topics a specific conflict. A request without either destination field fails validation before identity or persistence.

### 7. API credential lifecycle

Use `agent_api_keys` for user-owned credentials with public ID, secret digest, label, last four characters, creation time, last-used time, and revocation time. Generate independent random public IDs and secrets. Store only SHA-256 of the full secret-bearing credential, compare in constant time, and never log the bearer value.

Create through the signed-in account page after a Premium gate check. Return the secret once with `Cache-Control: no-store`; do not put it in URLs, local storage, analytics, or later list responses. List metadata, allow multiple named keys, and cap active keys at ten as an abuse limit. Revocation is immediate, idempotent, and available after downgrade. Recheck Premium entitlement on every API send; a downgrade pauses use without deleting existing entries. The key label is user-provided descriptive text, not evidence of which software holds it.

### 8. Imports with explicit selection

Parse ChatGPT/Claude JSON exports and their ZIP containers locally in a web worker, presenting conversation titles and dates before upload. Recognize versioned adapters for actual sanitized fixtures; never guess a structure and import everything. Accept pasted plain text through the same explicit preview/confirm flow.

Limit archive input, total decompressed content, and accepted transcript batch to `TOPIC_ATTACHMENT_MAX_BYTES` (10 MiB). Bound entry count and decompression ratio, reject traversal/encrypted archives, and ignore attachments, binaries, hidden tool payloads, and unsupported records. Revalidate normalized transcripts on the API. The server receives only selected conversations, one Personal Source Entry per conversation, with `origin: import` and no expiry. Cancellation or selecting none stores nothing. Browser parse buffers and object URLs are released on close.

Use content/provider/conversation fingerprints and a batch retry ID to avoid duplicate imports into the same Source. No connected OAuth grant or Premium plan is required. Pasted text uses the transcript Source. Retain at most 100 safe links per imported conversation, report omitted counts, and preserve selected text within the batch size bound. Native apps show “Import conversations on the web” at the same point, without a native file picker.

### 9. Email Carl

Use the digest address from `RESEND_FROM_EMAIL` for the recipient, Carl’s From and Reply-To. An event for another mailbox ends at the webhook. This lets development and production share a domain without replying to each other’s mail.

Verify the signed webhook and deduplicate the provider email ID. The worker retrieves the message from Resend, compares its From with the signed event, and requires the receiving server’s DKIM and DMARC passes. Resend reports a signing-domain mismatch as `gray`. Automated responses and acknowledgments end here. An authenticated unregistered sender gets sign-in guidance at the verified From. Free senders get the plans link. Neither case runs the matcher or consumes quota. [Resend authentication fields](https://resend.com/docs/api-reference/emails/retrieve-received-email)

Run the same content matcher used by the AI picker across all editable Topics. A subject or first body line beginning with `topic:` boosts matching names. Require a final score of at least 0.75 to file automatically. A fuzzy hint contributes at most 0.1 and requires a content match above 0.6. Each clear match receives a sender-owned entry in one sorted transaction. Charge one shared daily send and confirm with a numbered list of Topic links.

When no match clears the filing threshold, show up to five relevant editable Topics. If there are none, ask for an existing Topic name. Readers can reply with numbers, written names or both. Resolve names against current edit access. Keep numbering stable. If a referenced Topic has disappeared, ask for names again before filing anything.

Thread replies with the original subject and real RFC Message-ID, In-Reply-To and References. A mail client can send just “2” without quoting the list. While a choice is outstanding, retain the original provider reference, sender binding, original message ID and encrypted ordered Topic IDs. Retrieve the original from Resend only after authenticating the reader and correlating the reply. If the provider has discarded it, ask for a fresh message. A successful selection or account deletion clears the choices.

Use the same sender lock for email and AI sends. A competing scan may still reference the sender and Topic. Commit one spend, one item per destination and the encrypted reply intent atomically. Retry with the same provider delivery key. Discard the temporary reply snapshot after delivery or abandonment. An unrelated linkless reply ends silently. A new link in authored reply text makes a fresh send. Strip quoted replies but preserve deliberately forwarded content.

### 10. Summarization, retention, and spending

Debounce bursts for each sender's Topic context and retain durable pending revision, dirty time, retry state, and attempt spend. One Topic workflow can iterate independent sender contexts. A failed context must not starve other senders; a missing owner key or exhausted owner budget blocks that Topic’s pending rewrites recoverably. Build from retained entries only, newest first, bounded to 1,000 entries, 80,000 input characters and 8,000 output characters. Older items remain readable even when outside that processing window. Input is nonce-fenced as untrusted data. Stable embedding-only inputs keep suggestions deterministic; they store no new vectors or private text. Use the current Topic owner’s model key and Scan-style spend reservation/accounting for summarization. Keep `senderId` and `billingUserId` distinct in snapshots and spend records. Suppress content telemetry and charge each actual attempt once to the owner resolved at reservation. Commit only against the exact Topic/sender/revision, unchanged owner, and live authorization. A transfer before generation resolves the new owner; a transfer during generation invalidates the result without moving its already incurred cost. A later attempt uses the new owner. Never fall back to a sender or operator key. Missing sender keys do not block summarization when the owner can pay. Routing embeddings remain billed to the requesting sender; this change concerns summarization.

Two senders on one Topic produce two separate summaries, both billed to that Topic’s owner. One sender filing to several Topics produces separate entries and contexts, billed to each respective owner; no global summary or shared context row is introduced. Reusing a settled summary in Scans adds no summarization charge. Owner spend records disclose usage, not another sender’s content.

Sends, email, and imports remain encrypted until explicitly deleted. Deletion invalidates the sender's summary and annotations immediately and schedule a rebuild. Public Findings remain. Recheck all included sender revisions and permissions before each review model call and the final transaction. Search, external discovery, public embeddings, global Resource content, and unrelated Topics never receive the private text. Scoring for the destination Topic does, regardless of its visibility.

### 11. Public explanations and private annotations

Carry public Topic context and sender-private context as separate typed fields. The public field remains the input for search, shared reports, chat retrieval, and podcast preparation. Bound aggregate private scoring input within the existing review ceiling and disclose incomplete coverage. Retain opaque per-call context labels mapped to sender IDs in process memory, not names or email addresses in prompts. The model returns annotations only for supplied labels; unknown or duplicate labels fail validation.

For each (Finding, sender) pair, one structured scoring call returns a relevance score, numbered linked-page passage selections, and that sender's private annotation. Only that sender's private context enters the call. The server splits the bounded fetched page into numbered passages after deterministic delimiter/backtick removal. The model selects passage numbers; the server validates those numbers and constructs the public explanation from the corresponding page text. Model-written paraphrases never enter the public explanation. This makes public facts page-bound and prevents another sender's text from entering an annotation request. The highest relevance score determines ranking and the corresponding page excerpts; all relevant sender annotations are committed together with the public Finding after revision checks. Reserve the total bounded cost before starting any sender call, using the configured input/output prices and an 8,192-token output allowance with low reasoning effort. Charge returned usage before reading or validating structured output, including truncated answers. Missing or invalid passage numbers or a stale sender revision publish neither layer. Podcasts narrate only the verified public explanation.

Persist the public explanation and encrypted annotations in one transaction after rechecking every included context version. A re-score replaces the annotation set for that revision and clears obsolete annotations. If both layers cannot be produced and validated within budget, defer that private-context review rather than publish an incomplete or unsafe result. Plain Topics keep their existing scoring path. Size and reserve output budget for the bounded structured response.

The public `findings.relevanceExplanation` field remains the only explanation reachable by public feeds, metadata, MCP views and `read_findings`, topic reports, notifications, chat retrieval, and podcast scripts/audio. Private annotation reads remain sender-authorized through a separate no-store endpoint. Finding popovers and sheets show only the public note, with no private annotation block or annotation fetch. Encrypted derived annotations retain their existing lifecycle. Anonymous and other-sender views have no annotation, badge, count, or serialized private data. Podcast generation and publication use the public explanation even for Topics with Personal sources and after a visibility change.

Queued public links keep canonical URL deduplication, the existing safe-fetch boundary, durable Scan claims, and per-link outcomes. Source identity, sender preference, and private provenance remain Topic-local and sender-private; they never become global Resource text. One sender's Source deletion never removes another sender's content or queue. Retain exact outcome links in that sender's Personal sources section.

Persist the actual `personalSourceScoreBonus` on the Topic's Finding as 0, 0.05, or 0.10. Deliberate AI Agent sends, selected imports, and personal forwards use 0.10; newsletter and automatic/unknown provenance use 0.05. Recognize a manually forwarded newsletter through retained list headers or unsubscribe/preference links; an ordinary mention of newsletters is not sufficient. `packages/contracts/sourceScoring.ts` owns `PERSONAL_SOURCE_SCORE_BONUS = 0.10`, `AUTOMATIC_PERSONAL_SOURCE_SCORE_BONUS = 0.05`, and the existing custom bonus. Each insert/re-score adds the stored personal bonus when positive, otherwise the custom bonus. Clamp to one. An upsert retains the greater stored/current bonus so later Scans do not lose or accumulate bonuses after the original Source disappears. A stronger incoming personal contribution triggers review even when content/context hashes match, while a thumbs-down remains excluded. A data-preserving migration converts existing multipliers to actual bonuses without changing relevance scores or any original Personal sources items.

Reload score bonuses from live Topic-local claims and merge duplicate URLs by strongest contribution. Place queued links before existing Findings, chosen URL pages, and ordinary candidates; deliberate contributions lead newsletter/automatic ones. Bypass embedding work and the similarity floor for queued links. A missing embedding skips vector deduplication; available vectors and normal content hashes retain their existing duplicate checks. Every candidate still goes through safe fetch and model review, and only then receives its bonus. The bonus grants no max-results exemption. Deferred/stopped/failed work stays queued and budgets remain bounded. Another Topic sharing the global Resource gets no provenance or bonus.


### 12. UI, compatibility, and documentation

The latest flat-list decision replaces the earlier separate-button mockups. Use the existing Nightshift Topic info popup and Artisanal Blend card on web and mobile. All customer copy says **Personal sources**.

**One section in two placements.** Keep fetched **Sources** first, with `N of 10` using fetched rows only. Immediately after it, render the same `TopicPersonalSourcesSection` from core, with thin same-name platform adapters. Use one collapsed disclosure row: **Personal sources · N items** on the left in the existing muted Architects Daughter section-label type role and **Only you can see this** on the right. Expanding it reveals the entire section: the numbered item list. Each item has its own nested disclosure. Show the current sender’s total live item count beside the header label, using “1 item” for a single item. Refresh it after deletion; paging does not change the total. Reuse CoffeeLoading for compact **Steeping** states; the initial load shows one indicator for the item list. Read sender-only receipt metadata to show the section only when the sender has live items. Mount entry-text queries only after opening; closing the section hides all of its contents, cancels pending reads, and releases its decrypted pages and local paging state. Do not add a separate summary heading or item-count row. Number the newest-first item rows, continuing across numbered pages and restoring their positions when paging back. Use compact vertical spacing: no outer vertical padding on the section row, and four-pixel item-row padding and trigger padding at the base text scale, with existing minimum touch heights. Underline the primary label on hover or keyboard focus on web and while pressed on native; never fill the row as feedback. Keep the web focus ring and disclosure semantics. The final visible item keeps its bottom padding but has no divider; the section adds no extra bottom inset. Do not add a page button, separate popover, Email/Claude grouping, indented list wrapper, or nested padded card. The parent surfaces retain their ordinary layout and safe touch targets. Add the existing dotted/dashed separator above Personal sources in Topic info and below it in Artisanal Blend. The wrapper and its separators render only with live sender items. Item titles use the muted Architects Daughter font at regular weight, retaining their readable sentence case. Add no padding between the section trigger and the item list, and remove the first visible item’s top padding. Keep the internal scoring summary and its coverage helper text internal; neither placement fetches or displays them. Row numbers use regular Architects Daughter text without trailing dots. Give the numbered pagination controls equal eight-pixel spacing above and below, with no extra list-wrapper top margin.

**Item expansion.** Each row starts collapsed with its number, title, and received date, without a sender badge, and expands independently to sender details, exact stored text, links with persisted outcomes and Finding destinations, private references, and confirmed Delete at the top right of the expanded item, beside its receipt metadata. Place each link outcome immediately to the right of its link, wrapping when necessary; queued links say **Next brew**. Show at most five items per page with the existing numbered square Pagination controls shared by the apps. Direct page jumps read only the authenticated sender’s receipt IDs, dates, and ciphertext sizes to derive boundaries; decrypt only the selected page. Retain the two-MiB page budget and the single-large-import exception, so a large import may reduce the item count without skipping later items. Return actual page count, row offset, total count, and a clamped page number after deletion. Keep the previous cursor API compatible. Preserve accessible text paging inside large items. Expanded item content has equal eight-pixel top and bottom padding at the base text scale and no extra top margin. A successful deletion invalidates the internal scoring summary and refreshes every mounted item page and count in both placements; failure preserves content and offers retry. Empty topics keep their existing layout with no Personal sources section or added divider; a former editor with retained items and Topic read access sees their own history without new-send controls. No one can see another sender's data.

## Risks / Trade-offs

- **Model output crosses a public/private boundary** → Separate structured fields, page-evidence validation, private-only phrase checks, cross-sender canary evals, and atomic fail-closed persistence.
- **One bounded call cannot read unlimited permanent imports verbatim** → Retain the originals, apply deterministic input allocation, and disclose omitted coverage.
- **Deletion can race a model call or Scan** → Revisions, sender checks, rechecks, and compare-and-set persistence prevent stale private context from returning.
- **Domain labels are not vendor attestation** → Base identity on grants and exact registered hosts; never accept self-reported names as proof.
- **Uncertain routing** → Ranked editable Topic choices, strong-match recommendations, the email routing relevance floor, and clarification without storage.
- **Shared-address spoofing or reply loops** → Receiver-computed aligned DKIM and DMARC before any response, account matching before filing, own-message/auto-message suppression, bounded retries, and replies only to authenticated From.
- **Personal sources context reaches model infrastructure** → Topic-owner billing for summarization and review, with sender-only summaries, explicit privacy disclosure, and no prompt/output capture. Verify provider retention settings before release.
- **Source creation races stale clients** → Topic locking, concrete-identity uniqueness, explicit Personal sources deletion, and additive mobile endpoints.
- **Provider retries cost money** → Durable idempotency and attempt accounting; no exactly-once external billing claim.
- **Existing installed clients do not know Personal sources controls** → Preserve old payloads and saves; exercise a frozen-client fixture before rollout.
