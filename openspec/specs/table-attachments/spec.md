## Requirements

### Requirement: A table file is written as table text, never summarized

An attachment whose kind is a table file — `csv`, `tsv`, or `xlsx` — SHALL reach a Scan as its rows. Legacy `.xls` is out of scope: it is a binary BIFF workbook, not an OOXML zip, and the XLSX reader does not open one. Its context SHALL be written out as table text instead of generated by a model: a header line naming the file, the sheet, the row count, and the column names, then the header row and the data rows verbatim.

The header line SHALL be computed from the file, never generated. Every value in it is derivable from the file, so a model call would add cost, latency, and nondeterminism to produce a sentence already in hand, and the same file would stop producing the same context on every run.

Writing the table text SHALL take no model call of any kind.

#### Scenario: A spreadsheet's rows reach the scan

- **WHEN** a CSV attachment is processed
- **THEN** its stored context includes the header row and its data rows verbatim, under a computed line naming the file, the row count, and the column names

#### Scenario: Table text costs no inference

- **WHEN** a table file is processed
- **THEN** no model is called for its context

### Requirement: Table text is limited by rows and names what it omitted

Table text SHALL be limited by a maximum row count, `MAX_TABLE_ROWS`, not by a character length. When rows are omitted, the table text SHALL end with a line naming how many.

`MAX_TABLE_ROWS` SHALL be a constant, not a plan attribute: the same file must produce the same context on every account, and plan differentiation lives in `monthlyBudgetCents` and scan frequency.

Table text SHALL also be bounded by a character budget, and SHALL stop before the row that would exceed it, so a wide sheet cannot spend an unbounded budget on long rows. Neither bound SHALL be the merged-context character slice in `finalizeAttachment`, which cuts mid-row.

#### Scenario: A long spreadsheet is limited by rows

- **WHEN** a spreadsheet with more rows than `MAX_TABLE_ROWS` is processed
- **THEN** its context includes `MAX_TABLE_ROWS` rows and a trailing line naming the number of rows omitted

#### Scenario: Table text is never cut mid-row

- **WHEN** table text is stored
- **THEN** its final content line is a whole row or the omitted-row line, never a partial row

### Requirement: Every non-empty sheet is written as table text under one shared budget

A multi-sheet workbook SHALL project every non-empty sheet under its own heading, and the sheets SHALL share one row budget.

Projecting only the first sheet silently drops data when sheet one is a cover page or a pivot. A per-sheet limit multiplies the budget by the sheet count, so a workbook's cost would depend on how its author organized it.

#### Scenario: A two-sheet workbook writes both sheets

- **WHEN** a workbook with two non-empty sheets is processed
- **THEN** both sheets appear in the context, each under its own heading

#### Scenario: Sheets share one budget

- **WHEN** a workbook's sheets together exceed `MAX_TABLE_ROWS`
- **THEN** the total rows written across all sheets does not exceed `MAX_TABLE_ROWS`
