# CarlNotes domain model

> A **Topic** (owner = creator) is tuned with context and **Sources**; each **Scan** discovers **Resources** and appends **Findings** to the topic's **Feed**; users hold **Subscriptions**, a **Team** holds Topics together with a shared room on each, and **Integrations** connect Sources in and deliveries out.

| Entity | Is | Notes                                                                                                                                                                                                                                                                                                                                                                       |
|---|---|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Topic | the configuration | name, context doc, attachments (file in R2 + distilled context, generated once by the processing workflow after upload), frequency, visibility (public / invite / private), owner_id                                                                                                                                                                                        |
| Source | topic input: "pull from X" | kind: url, rss, reddit, youtube, podcast, search, bluesky, x, composio, plugin; `integration_id` nullable (RSS needs none); screening status (pending / ready / failed) + error — a url Source is skipped until its page screens clean: hidden from non-owners and skipped by Scans. A **default Source** is an ordinary Source the app configures for the owner from the registry in `shared/sources.ts` (search alone today), each created with no config, so a default kind's ingester must run without one. every other kind is a custom Source naming what to pull from — Google News is an `rss` Source whose feed covers one publisher. `search` and `x` authenticate with one operator-level key instead of a per-user Integration |
| Scan | one execution of a topic's pipeline | domain word; Temporal keeps "run" at the infra layer only                                                                                                                                                                                                                                                                                                                   |
| Resource | canonical external artifact, deduped globally | url, content hash, embedding, kind (read / watch / listen)                                                                                                                                                                                                                                                                                                                  |
| Finding | topic-scoped judgment about a Resource | relevance score, relevance explanation; one Resource → many Findings; a rating snapshots its rater onto the row, and `finding_feedback` (a user's own words) with `finding_views` (opened / dismissed / dwell) capture reading signal, record-only                                                                                                                                                                                                                                                                                                        |
| Feed | a topic's stream of Findings | the output side; "channel" is UI copy only                                                                                                                                                                                                                                                                                                                                  |
| Subscription | subscriber ↔ topic join | subscriber is a user (`subscriber_user_id` NOT NULL); delivery prefs live here; rows are created at self-subscribe, invite acceptance, or a Team join (which fans out muted rows for the Team's Topics), so `created_at` is the activation time; the owner holds one too, so scheduled deliveries reach them, but it is excluded from every subscriber count and `isSubscribed` check                                                                    |
| Team | a named set of users holding Topics together | `teams` (name, unique case-insensitive, bio, avatar, `is_public`) plus `team_members` (role: leader / member, `is_member_visible`, `is_active` — false is a **join request**: the row grants nothing and only leaders see it until one activates it, and every membership read filters to active rows); a team never loses its last leader. A team **holds** a Topic two ways: as its **owning team** (`topics.team_id`) or through a **share** (a `team_topics` row); **held topics** covers both, and a **holding team** is a team in either relation. Only a team the topic's owner leads may own it; when the owning team lets go, the oldest owner-led holding team becomes the owning team, and a team the owner does not lead only ever holds a share. Joining fans out muted Subscriptions to the Team's held Topics; two-value visibility — a public Team has a page and a byline on its public owned Topics (the **byline team** is the owning team), a private one shows nothing |
| Connection | whether two users have interacted, derived and never stored | derived at invite creation from a shared Team, an active subscription to a sender's Topic, or a previously accepted invitation; one function answers both the invite-access setting's connected value and the raised invite limit; no connection table, no friend-request flow, no stored graph |
| Chat Room Message | one message in a team Topic's shared room | `room_messages`: ordered bigint ids, nullable `author_user_id` beside `author_username` recorded at post time (Carl's rows record his name and no account reference), a reply reference, encrypted content; `room_mentions` notify named members; `room_summaries` hold the per-room running summary; a room exists per (Topic, holding Team), so a shared Topic has one room per holding team. A message **addresses Carl** through his @mention, @all, or a reply to his message, which starts his room turn; the **transcript** is the message window rendered for him, each line named by its author with reply quotes resolved |
| Invite | a consent-based offer of a Topic or a Team | `invites`, exactly one target per row, standing as a pending offer until accepted or declined. Two kinds: an **invite link** names nobody — a token url with limited uses and an expiry, revocable; a **user invite** names a person, as an **email invite** (mail sends) or a **username invite** (no mail — it waits on the recipient's own pages). **Live** = still redeemable: no revocation, no decline, no passed expiry, uses left; **pending** is the recipient-side word for an unanswered live invite. The **invite URL** `/invite/{token}` (`inviteUrl` in code) is the redemption address every invite includes, and **redeeming** it is the same transition accepting is; the **join page** renders it. Creation consults the recipient's `invite_access` setting and the sender's computed invite limit, scaled by **reputation** — the accepted share among the sender's week-old user invites, halving a low sender's limit, never below one a day; declined rows are saved with a `declined_at`, never deleted, so reputation stays measurable. **Withdraw** is client copy only: identifiers say revoke where `revoked_at` saves and delete where rows go |
| Kept Chat Attachment | a chat attachment a user marked keep | stored per user per Topic, summarized once, its summary read into that user's own later chat turns; limited; cleared with the conversation; a room turn never reads them, since its answer posts to the whole room |
| Integration | a user's connected external account | OAuth grant + scopes (Composio-managed or native); referenced by Sources (input) and Subscriptions (delivery)                                                                                                                                                                                                                                                               |
| Billing Subscription | a user's active Stripe subscription; the active row derives their plan | `billing_subscriptions`; free = no row; **distinct from Subscription** (a topic subscriber join) — never conflate the two                                                                                                                                                                                                                                                   |
| Bookmark | a per-user marker keeping a Finding | `bookmarks` mirrors `consumptions`; a bookmarked Finding is exempt from the max-results filter; never a `findings` column                                                                                                                                                                                                                                                   |
| Chat Turn | one question and its reply about a Topic | `chat_turns`; every chat turn writes a row because every chat turn is metered, and `question`/`answer` are kept only when the gate grants the sender `chat:persist`, so a chat turn without it is a cost row with null text; chat is signed-in only; the **chat ledger** is `chat_turns` itself, every spend a row; **solo chat** is the one-user topic Coffee Talk, in contrast to a team room; a **Chat Room Turn** is Carl's one reply in a room — his text posts as a room message and the spend writes a text-less ledger row naming it (`room_message_id`), billed to the member whose message addressed him; **never "Chat Session"** — `sessions` is Better Auth's sign-in plumbing |
| Note | a rich-text note on a page, with a visibility | `notes`: the **page** is the Topic or the Team it lives on (exactly one of `topic_id` / `team_id`), the **visibility** is `private` / `team` / `public`, and `owner_user_id` is the creator, who alone changes its visibility or deletes it; a private note is its owner's alone. The ydoc column is the source of truth for content and comment threads, the `html` column is regenerated from it on save so the default page load never needs the editor. Deleting a page cascades to all of its notes, other users' private ones included. `note_comment_threads` / `note_comments` mirror the ydoc's comment threads for counts and notifications. "Tasting Notes" is the section's UI copy; identifiers say note |
| Release | one published GitHub release, mirrored so the app never reads the GitHub API on a pageview | `releases`: keyed by `tag`, which GitHub allows one release per, so a re-delivered webhook and a re-run of the sync both upsert the same row; stores body markdown exactly as GitHub holds it and never rendered HTML, so nothing goes stale when a body is edited; `is_prerelease` is stored and filtered on read. a release is written on GitHub and read at `/releases`, so there is never a second changelog. Never "changelog" for the entity: that is the path `/changelog`, which redirects |
| Username | a user's public name, and the only identity a stranger sees | `users.username` plus `users.username_normalized` for case- and separator-insensitive uniqueness, both NOT NULL: the name is drawn inside the signup insert instead of a moment after it, so a row is never nameless. generated so signing up stays one step, changed later from the account page. display only: a profile is addressed by user id, so no link points at a name and a name can be changed freely, with no history and no limit. the reserved list in `shared/usernames.ts` withholds staff impersonations and every top-level route slug, so a future vanity url can never collide with a name; a new top-level route adds its slug to the list |
| Avatar | a user's public image | `users.avatar_source` (generated / oauth / upload) with `users.avatar_key` for the stored image; generated from the username by default; the OAuth photo Better Auth writes to `users.image` stays private until the user opts in, since signing in is authentication and publishing a face is a separate decision |

## Layering rules
- Integration = the credential; Source = an input use of it; delivery = an output use of it. Connected once, reused everywhere.
- Ingester = worker code turning a Source into Resources (see ingester-authoring). One composio ingester; toolkit variety lives in Source config, not code.
- `shared/sources.ts` holds both source tables: the default Sources every new Topic starts with, and the options the custom picker offers. An entry names the Source kind it saves as and builds its config, so a new Source is an entry instead of a kind or a special case. An option is not always a kind: Google News saves as `rss`.
- Topic authority is `topic.owner_id`; the single platform override is an `admin` (`users.role`). Every authority **and** entitlement check routes through one `isAllowed(user, capability, resource)` gate — never a scattered `role ===` or `tier ===`. The gate resolves a user's **effective role** on a Topic — owner / leader / member / none, the strongest grant across the owning and holding teams. Topic access is still "a Subscription path exists."
- Entitlements come from the user's **plan** (`free`/`plus`/`premium`), derived from the active Billing Subscription (free = no row) and resolved by the gate.
- Invites are consent-based: the Invite row above holds the kinds and their lifecycle. A topic invite grants topic-page view and stands as a pending subscription offer; a team invite offers the join. On invite Topics a subscriber sees only Findings from Scans started after their activation; the owner always sees full history. One Scan serves every subscriber — the amortization the pricing model assumes.
- A Resource is raw and global; a Finding is scored and topic-scoped. Don't blur them. A Resource may include a captured `engagement` count (like a reddit score) that read-side ranking uses.
- A Scan closes by filtering the Topic to its `max_results` best Findings by relevance; bookmarked Findings are never filtered.
- A Scan traces every Source that did not deliver normally in `scans.problem_sources`: one that fell back to a keyless path records its `fallbackMode`, one that failed records its `reason`. A problem is independent of `status` — a Scan whose Sources all succeeded, some of them through a fallback, is still `succeeded`.
- A Scan has **one Budget**, created before ingestion. Every stage charges into it — `ingestion` (the Sources' own spend: Exa for `search` and TwitterAPI.io for `x`), `embedding`, `fetch`, `scoringCheap`, `scoringPremium` — so `Scan.cost` is that Budget's total and `stage_costs` is its breakdown, and the one spend limit sees everything the Scan charges. Never sum a separately tracked ingestion number alongside it.
- A paid ingester reports the dollars it really spent, never zero, and bounds one Scan's spend with its own read limit. The Budget is charged once after every Source returns, so a Source cannot consult it mid-run and the limit has to hold without one.

## Auth infrastructure is not domain vocabulary
Better Auth manages `users`, `sessions`, `accounts`, `verifications` — identity/access plumbing, the same tier as `users` itself, never content-domain nouns. `accounts` is sign-in identity only (a password credential or an OAuth grant used to authenticate) and is never referenced by a Source or a Subscription. **Integration** stays the sole representation of a connected external account used for sourcing or delivery (e.g. Composio-managed Gmail) — never conflate the two, and never resolve Source/delivery credentials through `accounts`.

## Rejected terms — never introduce
- "Channel" (use Feed)
- "Item" (use Resource or Finding)
- "Update" (CRUD collision; use Scan or Finding)
- "Run" (Temporal's word, infra layer only; use Scan)
- "Crawl" (names one stage of five)
- "Group", "List", "Cohort" (use Team)
- "Org", "Workspace" (use Team)
- "Audience" (use Team)
- "Addressed" as an invite noun (use user invite; "a message addresses Carl" keeps the plain verb)
- "typed-email" (use email invite)
- "Viewer" (a signed-in person is a **user**, a logged-out one is a **visitor**; see below)

## User and visitor name the two states of the person on the page
A **user** is signed in; a **visitor** is not. Identifiers and comments say user where an account is
required — a role, a subscription, a wallet, anything keyed by `user_id` — and visitor only where the
person has no account yet, which is the sign-up and join copy. Never "viewer": it named both states at
once, so `viewerRole` and `viewerUserId` read as if a logged-out person could hold a role. Where the
subject is already unambiguous the qualifier drops entirely: `isLeader`, `role`, `userId`.

## Page is the Topic or the Team a thing lives on
A **page** is exactly one Topic or one Team, and it is what a Note sits on and what a private Chat Turn
is addressed by. `NotePageRef` and `ChatPage` are the same pair, and `notes` stores it as a nullable
`topic_id` and `team_id` under a check constraint. Never "scope", which already means the chat
attachment's reach, an OAuth grant's permissions, and a Temporal `CancellationScope`. Never "subject",
which already means an email's subject line and the target of a flagged report. A Note's own
`private` / `team` / `public` setting is its **visibility**, never its scope.

## Follow and subscribe are one concept: follow is the client-facing word, subscribe is the code word
Client-facing copy says **follow**, **follower**, and **following**. Every identifier says **subscribe**, **subscription**, and **subscriber** — tables, columns, types, functions, routes, and analytics events alike. The boundary is crossed exactly once, where a string is written for a user to read. Never rename a table toward the copy, and never let `follow` reach an identifier: a codebase that says both has two names for one thing and no way to tell which a given `follower_count` means.

## Never "surface" for a page or a feature
A **page** is a page. Say `/releases`, the team page, the topic editor, the webhook route: name the
thing. "Surface" says only that a reader might encounter it, which is true of everything and tells the
next reader nothing. It also invites lumping unlike things together, as in a "release notes surface"
that included an inbound webhook nobody looks at. The verb keeps its meaning — an error is surfaced to
a caller — and so does the visual noun, where a card sits on a sunken surface.

## Rules
- Singular entity names in code (`Finding`), plural tables (`findings`).
- New domain nouns get a row in the table above before they appear in code, a table, or a route.
