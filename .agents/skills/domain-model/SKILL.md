# CarlNotes domain model

> A **Topic** (owner = creator) is configured with context and **Sources**; each **Scan** discovers **Resources** and
> appends **Findings** to the topic's **Feed** and may render a **Podcast Episode** that narrates them; users hold
> **Subscriptions**, a **Team** holds Topics together with a shared room on each, and **Integrations** will connect
> Sources in and deliveries out.

| Entity | Is | Notes                                                                                                                                                                                                                                                                                                                                                                       |
|---|---|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Topic | the configuration | name, context doc, attachments (file in R2 + context, written once by the processing workflow after upload: a short file as written, a long one summarized), frequency, visibility (public / invite / private), owner_id; the page url is `/topics/<id>/<slug>`, where the **slug** is the name as url-safe words (`toTopicSlug` in `packages/contracts/seo.ts`), or `/topics/<id>` alone for a name with no url-safe characters. The id alone resolves the Topic, and a url by id alone or with a stale slug redirects to the current url. A public Topic is **shown** once it has at least `MINIMUM_SHOWN_FINDINGS` Findings (`isPublicAndShown`). The homepage's Featured topics and Popular sections, the sitemap, `llms.txt`, and the public part of the MCP topic list include a public Topic only once it is shown |
| Prompt Version | one saved text of a Topic's prompt | `topic_prompt_versions`: one row for the first prompt and one for every change, with the prompt, who saved it, when, and its `origin`: editor, chat, or mcp. An unchanged save writes nothing. `saved_by_user_id` goes null when that account closes. Rows are never updated and have no version number. The time order is the history |
| Topic Tool | one action Carl or an agent takes on a Topic, or to make one | `apps/api/tool/`: `updateTopicPrompt`, `updateTopicFields`, `addTopicSource`, `removeTopicSource`, `createTopicFromDraft`, `suggestTopicDraftSources`. Each takes the user and asks its own gate: `topic:edit` on the Topic for the edit tools, `topic:create` and the daily suggestion limit for the draft tools. Two **adapters** expose them. The chat adapter takes the Topic from the chat's page and binds the tools only for a user the gate grants `topic:edit`. It binds no saving tool, in the private chat and a Topic's team chat room alike: Carl previews a change, and the server applies that preview through the Topic Tools only if the user's next message agrees, the **proposal** rule under Chat Turn. In a room the preview belongs to the member Carl showed it to, and only that member's next message to him can agree, so no other member's yes ever saves it. On the proposing turn he calls `proposeTopicEdit`, which saves nothing and only puts the Topic's card in front of the user, so the card shows while an edit is under way and not otherwise. It and `cancelTopicEdit`, which takes the change back off the card, are the chat adapter's alone: the MCP adapter offers neither, since its client runs its own approval. Both are bound on the `topic:edit` grant. A proposed change stands only until the user's next message on that page, which takes it whether or not it agrees, or until Carl cancels it with `cancelTopicEdit`, so a yes answering some later question never saves an old preview. The MCP adapter takes the Topic as an argument, or from the topic-bound route, and leaves confirmation to the client. Editing never starts a Scan. The new-topic chat adds `draftTopic`, which writes the Topic Draft, and `proposeNewTopic`, which saves nothing; the server creates the Topic through `createTopicFromDraft` only if the user's next message agrees |
| Topic Draft | proposed Topic settings shown for confirmation in chat or through MCP | The new-topic chat uses `topic_drafts`, one row per user, holding a name, a prompt, Sources as source option and value pairs, invite emails, the visibility, the team it joins, and the settings. The browser sends it with every turn, takes it back from the tool calls the reply streams, and reads the stored one back when the conversation loads. The files the user attached stay in the browser until the topic exists. `createTopicFromDraft` saves it through the editor's own create path, and the chat row is deleted when the Topic is created or the chat is cleared. MCP previews the same settings with a confirmation signed for the user, client, draft, and expiry. Confirming stores a one-time confirmation with the created Topic |
| Source | one Topic input, fetched or received | kind: url, rss, reddit, youtube, podcast, search, bluesky, x, composio, plugin, ai_agent, email; screening status (pending / ready / failed) + error. A url Source stays hidden from non-owners and skipped by Scans until screening succeeds. A **default Source** comes from `packages/contracts/sources.ts` (search today), with no config. Other fetched Sources name what to pull from; Google News is an `rss` Source. `search` and `x` use an operator key. **AI Agent** and **Email** are receiving Sources on any Topic the sender can edit. Each receiving Source belongs to one sender and one concrete delivery identity within its Topic. `ai_agent` identifies an authenticated OAuth client, a user-owned API key, or an explicit conversation import. `email` receives independent requests at the topic scan email mailbox from `RESEND_FROM_EMAIL`. **Email Carl** requires Plus or Premium and an authenticated account email. Clear editable Topic matches save atomically only with a nonempty `topic:` hint in the subject, then receive a **confirmation email**. Without that subject hint, even strong matches require the sender’s choice before saving. A first-body-line hint affects ranking only. A same-thread **clarification email** offers numbered Topics and accepts numbers or written existing Topic names. A clear fuzzy name is accepted; ambiguity asks again. Only provider/thread references and encrypted Topic choices are retained before selection, with no pending email body. Successful selection removes that metadata and counts once. Cancellation, capacity, and already-filed emails are absent. Receiving Sources are ready on creation and use dedicated setup/removal actions. Identifiers say `aiAgent`; stored kinds say `ai_agent`. |
| Personal Source Entry | one deliberately received summary, email, or imported conversation | Customer copy says **item** in Personal sources. Code uses `PersonalSourceEntry`. The `personal_source_entries` table stores the Source, Topic, sender, origin (`send`, `email`, `import`), received and summarized times, and encrypted title, text, sender, links, and optional sender-only chat reference. All entries remain encrypted until explicitly deleted. Age alone never removes their content or scoring eligibility. Entries supply private context and queue public links, never become Resources or Findings themselves. Items and summary remain sender-only through ownership and visibility changes. Their text and links inform scoring only on their destination Topic. Podcasts narrate the public explanation alone. |
| Scan | one execution of a topic's pipeline | domain word; Temporal keeps "run" at the infra layer only                                                                                                                                                                                                                                                                                                                   |
| Resource | canonical external artifact, deduped globally | url, content hash, embedding, kind (read / watch / listen)                                                                                                                                                                                                                                                                                                                  |
| Resource Image | an image of a Resource's own page, stored for the films that narrate the Resource | `resource_images`: the Resource, its position, the object key at `resources/<id>/images/<position>.jpg`, the stored width and height, the source url, and whether it is the page's **link preview image** (`is_link_preview_image`). `resources.images_fetched_at` records that the fetch ran, with or without an image, and `images_filter_version` the image filter version it ran under. The fetch runs the first time a film narrates the Resource, and again under a newer filter version, from the Markdown the Scan stored and the page's link preview image, with every fetch through the public url guard. It keeps at most six: shown by the page's main content outside any link, a jpeg, png, webp, or avif, at least 200 pixels on its shortest side, a shape from 9:16 to 4.5:1, at least 64 colors or, for a black-and-white photo, 12 levels of its gray pixels, never a logo, icon, ad, or tracking pixel, and one copy of each picture. Each is stored within 2560 by 1440. An unsafe Resource has none. Identifiers say `resourceImage`, never `pageImage`, since a page is the Topic or the Team a thing lives on |
| Finding | topic-scoped judgment about a Resource | relevance score, relevance explanation; one Resource → many Findings; a rating snapshots its rater onto the row, and a Finding rated thumbs down stays stored but leaves every feed read and count and never scores again, and `finding_feedback` (a user's own words) with `finding_views` (opened / dismissed / dwell) capture reading signal, record-only                                                                                                                                                                                                                                                                                                        |
| Private annotation | a sender-only explanation of how a Finding relates to their Personal sources | `finding_personal_annotations`: encrypted text keyed by Finding and sender. Written with the public explanation in one model call, read through a private endpoint, and excluded from public feeds, shared exports, and Podcast Episodes. |
| Feed | a topic's stream of Findings | the output side; "channel" is UI copy only                                                                                                                                                                                                                                                                                                                                  |
| Subscription | subscriber ↔ topic join | subscriber is a user (`subscriber_user_id` NOT NULL); delivery prefs live here; rows are created at self-subscribe, invite acceptance, or a Team join (which fans out muted rows for the Team's Topics), so `created_at` is the activation time; the owner holds one too, so scheduled deliveries reach them, but it is excluded from every subscriber count and `isSubscribed` check                                                                    |
| Team | a named set of users holding Topics together | `teams` (name, unique case-insensitive, bio, avatar, `is_public`) plus `team_members` (role: leader / member, `is_member_visible`, `is_active` — false is a **join request**: the row grants nothing and only leaders see it until one activates it, and every membership read filters to active rows); a team never loses its last leader. A team **holds** a Topic two ways: as its **owning team** (`topics.team_id`) or through a **share** (a `team_topics` row); **held topics** covers both, and a **holding team** is a team in either relation. Only a team the topic's owner leads may own it; when the owning team lets go, the oldest owner-led holding team becomes the owning team, and a team the owner does not lead only ever holds a share. Joining fans out muted Subscriptions to the Team's held Topics; two-value visibility — a public Team has a page and a byline on its public owned Topics (the **byline team** is the owning team), a private one shows nothing |
| Connection | whether two users have interacted, derived and never stored | derived at invite creation from a shared Team, an active subscription to a sender's Topic, or a previously accepted invitation; one function answers both the invite-access setting's connected value and the raised invite limit; no connection table, no friend-request flow, no stored graph |
| Chat Room Message | one message in a team Topic's shared room | `room_messages`: ordered bigint ids, nullable `author_user_id` beside `author_username` recorded at post time (Carl's rows record his name and no account reference), a reply reference, encrypted content; `room_mentions` notify named members; `room_summaries` hold the per-room running summary; a room exists per (Topic, holding Team), so a shared Topic has one room per holding team. A message **addresses Carl** through his @mention, @all, or a reply to his message, which starts his room turn; the **transcript** is the message window rendered for him, each line named by its author with reply quotes resolved |
| Invite | a consent-based offer of a Topic or a Team | `invites`, exactly one target per row, standing as a pending offer until accepted or declined. Two kinds: an **invite link** names nobody — a token url with limited uses and an expiry; a **user invite** names a person, as an **email invite** (mail sends) or a **username invite** (no mail — it waits on the recipient's own pages). **Live** = still redeemable: no decline, no passed expiry, uses left; **pending** is the recipient-side word for an unanswered live invite. The **invite URL** `/invite/{token}` (`inviteUrl` in code) is the redemption address every invite includes, and **redeeming** it is the same transition accepting is; the **join page** renders it. Creation consults the recipient's `invite_access` setting and the sender's computed invite limit, scaled by **reputation** — the accepted share among the sender's week-old user invites, halving a low sender's limit, never below one a day; declined rows are saved with a `declined_at`, never deleted, so reputation stays measurable. **Withdraw** is client copy only: identifiers say delete, since a withdrawn invite's row is deleted |
| Push Device | one phone's Expo push token, bound to the session that registered it | `push_devices`: the unique token, the user and the session (both cascade, so sign-out, an ended session, and closing the account unbind it; a second account that registers the token takes the row over), the platform, the app version, and the last-seen time. A **push notification** is one of two **kinds**, `topic-scan` (a scheduled Scan's new Findings, sent to the topic scan email recipients with `users.is_topic_push_enabled` on) and `chat-mention` (a room message's `room_mentions`, sent to the named members with `users.is_chat_mention_push_enabled` on); both preferences are null until the first grant. `push_notification_sends` records each push the service accepted, one per event, recipient, and phone, with its ticket and receipt. Copy says **notification**, identifiers say **push**; never a bare "alert" for one |
| Kept Chat Attachment | a chat attachment a user marked keep | stored per user per Topic, summarized once, its summary read into that user's own later chat turns; limited; cleared with the conversation; a room turn never reads them, since its answer posts to the whole room |
| Integration | a user's connected external account | OAuth grant + scopes (Composio-managed or native); will be referenced by Sources (input) and Subscriptions (delivery). Planned: no table exists yet — the unused scaffold was dropped 2026-09                                                                                                                                                                                                                                                               |
| Billing Subscription | a user's active paid subscription from Stripe, the App Store, or Google Play; the active row derives their plan | `billing_subscriptions` with its `provider` (`stripe`, `app_store`, or `play_store`), one row per user; free = no row; RevenueCat delivers the two stores' purchases. A provider's **billing projection** is the row it reports, and another provider's row stays unless the projected plan ranks higher. The **store sync** re-reads the user's RevenueCat customer into the row after an app purchase or restore. The **RevenueCat app user id** is the random id per user (`users.revenuecat_app_user_id`) the app logs in to RevenueCat with, never the user id. The **storefront** is the country of the store account that buys, read from the store and never from the device's locale. The **store offering** is what the store sells on that storefront, and the **purchase offers** are what the app or the web may sell the user and where a paid plan is managed, decided by the storefront purchase rules in `packages/core/lib/storefrontPurchaseRules.ts`. A **sandbox purchase** is a store test purchase, which counts only in dev and for the listed accounts; **distinct from Subscription** (a topic subscriber join) — never conflate the two |
| Bookmark | a per-user marker keeping a Finding | `bookmarks` mirrors `consumptions`; a bookmarked Finding is exempt from the max-results filter; never a `findings` column                                                                                                                                                                                                                                                   |
| Consumption | a per-user record that a user read a Finding | `consumptions`; customer copy says Mark read; the newest `consumed_at` is the last read time; never a `findings` column |
| Job Lease | one run's hold on a job that must not overlap itself | `job_leases`, keyed by the job's name; `runWithJobLease` takes it, renews it while the task runs, and deletes it when the task ends |
| Podcast Episode | one rendered audio episode of a Topic, narrating Findings as a two-speaker script | `episodes`: the Topic, the user that it bills (its Scan's owner), the Scan that started it (at most one Podcast Episode per Scan), a status (`recording` / `published` / `failed` / `removed`), a title and description written before any audio renders, a season (the UTC publish year) and a number assigned only on publish, the audio's object key, byte size, and duration, the cost, and the script that passed its checks. The **outline** is the plan that the first script call writes, with the title, the description, and the **segments** in order, each a theme with its Findings and their planned minutes. A segment has a **transition** into it and its **chapters**, and a chapter narrates one Finding. The first segment opens with the **cold open** and the last segment ends with the **sign-off**, then the **goodbye**, a fixed opening exchange followed by the hosts' own closing turns. A **turn** is one host's spoken line, which is not a Chat Turn. `episode_chapters` join a published Podcast Episode to the Findings that it narrates and keep each Finding's Resource, so the next Podcast Episode plans a narrated Resource after the Findings that no episode narrated. A chapter keeps a user's rating once its Finding is filtered out, and a later Finding of its Resource on the Topic takes that rating and becomes the chapter's Finding. `episode_listens` is a user's own plays, progress, and completion, never a Podcast Episode column. `episode_feed_tokens` holds one listener's podcast feed token for one private or invite Topic. Removing a Podcast Episode, which its Topic's owner and an admin may do, deletes its audio, chapters, script, and listens and keeps the row as `removed`, so its number is never reused and its cost still counts. A **cover** is drawn per Topic (the show cover) and per Podcast Episode, at a url whose key changes with its title. A Topic's **podcast** is its setting and its feed of Podcast Episodes (`topics.is_podcast_enabled`, `podcast.xml`), which is not the `podcast` Source kind, an input that the app reads. The two hosts' names live in prompt and customer copy only: the script's speakers are `host` and `cohost` |
| Topic Podcast Episode Video | a Podcast Episode's film: the same Podcast Episode in a second format, its audio over drawn images with captions | `topic_podcast_episode_videos`, one row per Podcast Episode: a status (`rendering` / `ready` / `failed`) and the failure reason, the object keys of its three video-only **parts** (the **intro**, the **chapters**, and the **sign-off**), the joined **film** that plays and its WebVTT **captions**, its byte size and duration, the film's own **image** (`image_hash`, `image_origin`, `image_prompt`: one 1280 by 720 jpeg at `episodes/<id>/video/image-<hash>.jpg`, which the poster shows, beside its 2752 by 1536 **original** at `image-<hash>-original.jpg`, which the intro and the sign-off zoom into. It is drawn wide in the film house style the first time the film renders, and an editor regenerates it against `imageRegenerationLimit` or uploads one), the hash of the image the intro and sign-off were drawn from (`rendered_image_hash`: the film's own, or the Podcast Episode's or its Topic's until the film has one), the **render version** its stored film was rendered at (`render_version`, 1 for a film from before versions) with the version whose re-render failed for good (`failed_render_version`), and the cost of the image, the generated images, the render, and every rebuild. A chapter is a **montage**: its **shots** in order, each one image on screen for 5 to 8 seconds with one **move** (zoom in, zoom out, pan left, pan right), crossfaded into the next. The shots show the chapter's Resource Images, then its generated images, then the podcast card, and again from the first. Identifiers say `VideoShot` and `VideoShotMove`, and montage stays a word for comments and docs. An **generated image** is an image drawn for a chapter so that it shows one distinct image for every 30 seconds, and at least two, once its Resource Images and the podcast card are counted. A chapter draws at most 12 and a film at most `generatedChapterImageLimit`, 40 by default, each from the Finding's title and public relevance explanation alone, in the film house style, in a framing of its own. It passes the image moderation and is stored with no row of its own, the first at `episodes/<id>/video/chapter-<position>-image-s<style>.jpg` and each further one at `chapter-<position>-image-s<style>-<number>.jpg`, where the style is the version of the film's house style it is drawn in and style 1 has no `-s<style>` part. Any failure leaves the chapter on the images it has. Identifiers say `generatedChapterImage`. A **re-render** draws a ready film again at the current render version while the stored film keeps playing, then swaps the files in one update, and the backfill re-renders every ready film below the current version. A Podcast Episode plays in one **format** at a time, `audio` or `video`, and `episodes.video_play_count` counts its film's plays beside `play_count`. Every Podcast Episode published after the feature gets a film, and of the older ones only each Topic's latest, through the backfill. A render skipped for its owner's spent budget leaves a `failed` row with the reason `spend-cutoff`, which the backfill never renders. Identifiers say `topicPodcastEpisodeVideo`, and customer copy says **film**: **Coffee Break films** is the list on the topic page, a film card shows the film's own image and its play button, labeled Play film, opens the film and plays it, **Video** opens the film from a Brews News row, **Edit film** in the action menu of the podcast episode page and of the topic page opens the film's image for an editor, **Mute** turns off the film's sound, the film's own play continues the audio as the film, and the audio player card's play continues the film as audio. The audio player card has no button for the film. **Coffee Break Cinema** is the film's section on the topic page, right above **Coffee Break podcast**, and on the podcast episode page, right under it, and the headphones right after both titles open the theme song's credits. The **film feed** lists the films beside the podcast feed. An admin pins a film to the home's **Featured films** through `home_order`, and a Topic's owner pins it to their Café's **Featured Films** through `profile_order`, apart from the podcast episode's own pins. A team page's **Featured Films** lists its Topics' films by those `profile_order` pins, then the most listened one of each other Topic, and a team has no pins of its own. Never movie, clip, or recording |
| Topic Cinema | the collapsible section under a Topic's header that plays the Topic's latest film, or a film chosen from Coffee Break films | It opens on every page load, and a collapse lasts for that visit alone, like the Coffee Break podcast section. Identifiers say `topicPodcastEpisodeVideoSection`. Customer copy says **Coffee Break Cinema**, the title of the podcast episode page's film section too, and never Topic Cinema, which names the Topic's section in comments and change docs alone |
| Topic Image | the one image every Topic has, at three sizes | `topic_images`, one row per Topic: the `hash` of the stored **original** (a 1264 by 848 jpeg, never a size), the **origin** (`generated` by the image model from a **scene** the prompt writer wrote, or `uploaded` by an editor), the scene, the model, and the cost. `topics.image_hash` copies the hash so every Topic read has it. The **sizes** are `page` (360 by 240 CSS pixels, the topic page header and the cards), `list` (120 by 80, the Topics rows and the findings MCP view header), and `thumbnail` (48 by 32, the search rows), each stored at 1x and 2x as webp under `topic-images/<topicId>/<hash>/`, served at `/api/topic-images/<topicId>/<hash>/<file>`. The **house style** is one fixed paragraph appended to every image prompt so every card looks like one family. A Podcast Episode's cover is drawn over its Topic's image, and its key includes the hash. Copy says **image**, never picture, artwork, or thumbnail for the whole; never brief or digest anywhere |
| Topic Image Render | one attempt to draw a Topic's image | `topic_image_renders`: the Topic, the user it bills (null for an admin's or the backfill's, on the platform's budget), the `kind` (`create` on the first save, `regenerate` by an editor on the better model with an optional one-line **hint**, `admin` from the Reports view, `backfill` from the one-off workflow, `resize` for a rederive of the sizes), the model, the status (`pending` / `succeeded` / `failed`), and the cost. The `renderTopicImageWorkflow` on the `topic-images` queue writes the scene, then renders and stores the files, falling back to the drawn covers. A render names the Podcast Episode, the Topic Post, or the film whose image it draws (`podcast_episode_id`, `topic_post_id`, `topic_podcast_episode_video_id`), or none for the Topic's own. An editor's **regenerations** of all of them count against one `imageRegenerationLimit` a month, shown as X of Y, and the button is absent at the limit |
| Home Topic | a Topic the home shows first, in its section that copy calls Featured topics | the admin's pinned `topics.homeOrder` (the `feature_order` column), then the trending public shown Topics. Identifiers say home, never featured, and a person's own pins say profile. Customer copy says Featured topics |
| Home Podcast Episode | a Podcast Episode the home shows first, in its section that copy calls Featured podcasts | the admin's pinned `episodes.homeOrder` (the `feature_order` column), then the most listened, one per Topic. Identifiers say home, and customer copy says Featured podcasts. The home films follow the same rule over Podcast Episodes with a ready film, through `topic_podcast_episode_videos.home_order`, in the sections that copy calls Featured films and New films this week, right before the podcast sections |
| Profile Topic | a Topic its owner pins to the top of their profile page, in the section that copy calls Featured Topics | the owner's pinned `topics.profileOrder` (the `profile_order` column), contiguous from one and at most twelve per owner, then the owner's other Topics in the home's trending order. Only a public Topic holds one, and only its owner sets it, through `profile:setProfileOrder`. Identifiers say profile, never featured. Customer copy says Featured Topics |
| Profile Podcast Episode | a Podcast Episode its Topic's owner pins to the top of their profile page, in the section that copy calls Featured Podcasts | the owner's pinned `episodes.profileOrder` (the `profile_order` column), with the Profile Topic's rules, then the published Podcast Episodes of the owner's Topics by listener count, one per Topic. Identifiers say profile, and customer copy says Featured Podcasts |
| Home Topic Post | a Topic Post the home shows first, in its section that copy calls Featured posts | the admin's pinned `topicPosts.homeOrder` (the `home_order` column), then the newest published, one per Topic, of public shown Topics. Right after it the home lists the Topic Posts of public shown Topics published in the last seven days, newest first, in the section that copy calls New posts this week. Identifiers say home, and customer copy says Featured posts and Home posts |
| Profile Topic Post | a Topic Post its author pins to the top of their profile page, in the section that copy calls Featured Posts | the author's pinned `topicPosts.profileOrder` (the `profile_order` column), contiguous from one with no limit, then every other published Topic Post of the author, newest first. Only a published Topic Post of a public Topic holds one, and only its author sets it. A team page lists every published Topic Post of its Topics that the reader may open the same way: the pinned ones in that order, then the rest newest first. Identifiers say profile, and customer copy says Featured Posts |
| Chat Turn | one question and its reply, about a Topic, about a Team's room, or about the Topic being made in the new-topic chat | `chat_turns`, whose `topic_id` names the Topic and is null on a team chat room's turn, which names the team instead, and on a new-topic chat turn, which names neither since no Topic exists yet; every chat turn writes a row because every chat turn is metered, and every row names its `kind`: `private` for a private chat turn on a Topic, a Team, or the new-topic chat, `podcast` for a **podcast chat turn** asked from the podcast player during one chapter of a Podcast Episode (it stores the Podcast Episode, the chapter's position, and the answer's speaker, `host` or `cohost`, never a host's name, and its stored question ends with a note naming the Podcast Episode, the chapter, and the host who answered, which the chat shows as a tag), `topic_post` for a **Topic Post chat turn** asked on a Topic Post's page (it stores the Topic Post in `topic_post_id`, which clears if the post is deleted, reads the post and its shared Comments, binds no Topic Tool, and shows in the Topic's private chat with a tag naming the post), `chat_room` for a Chat Room Turn, and `transcription` and `speech` for voice spend rows; check constraints hold each kind's shape, and a read tells rows apart by `kind`, never by which columns are null; `question`/`answer` and `tool_calls` are kept only when the gate grants the sender `chat:persist`, or when a Topic Tool ran, so a save is never invisible, and a chat turn with neither is a cost row with null text; `tool_calls` keeps what the chat turn's tools called and returned, encrypted like the text and replayed into the model's history so a save reads as a call; a **proposal** is the change Carl previewed in a chat turn, the edit `proposeTopicEdit` named or the draft `proposeNewTopic` proposed, kept in `chat_proposals` until the user's next message on that page, which applies it only if an agreement check reads that message as agreeing: a private chat keeps a keyed digest, and a Topic's team chat room keeps the preview itself, encrypted, in `topic_edit`, for the member it was shown to and the team whose room showed it (`team_id`); chat is signed-in only; **solo chat** is the one-user topic chat, in contrast to a team room; a **Chat Room Turn** is Carl's one reply in a room — his text posts as a room message and the spend writes a text-less chat turn row naming it (`room_message_id`), billed to the member whose message addressed him; a **spoken** chat turn is one whose question arrived by voice (`is_spoken`, on `chat_turns` and on `room_messages`), answered aloud, with the flag kept on the row so a reload and another device still read the turn as spoken; Carl's reply read aloud is the **spoken answer**, played one **spoken part** at a time (the first ends at its first sentence, then one per paragraph), and **listen mode** is the session one mic tap starts, which reopens the mic once his spoken answer finishes; ## MCP Apps, MCP views, and UI resources

**MCP Apps** names the extension. An **MCP view** is the UI running in the host's iframe. A **UI resource** is the `ui://` HTML template the server declares for it. A UI resource is not an ingested Resource.

Use the full `mcpView` or `McpView` in identifiers, types, components, helpers, and filenames: `McpView`,
`McpViewShell`, `SearchMcpView`, `TopicMcpView`, `callMcpViewTool`, and `mcpViewHost`. Never use bare `view`/`View` or
`card`/`Card` for this concept. Plural collections use `mcpViews`, `MCP_VIEWS`, or `mcp-views` where kebab case is
required. Resource names say `UiResource`, as in `toMcpUiResourceUri` and `registerMcpUiResources`.

Comments, engineering docs, and Storybook groups say **MCP view**, including when the surrounding module already names MCP. Framework names such as React Native's `View` and ordinary page-view counters keep their meanings.

Nightshift's `Card`, `InfoCard`, and `PlanCard`, Personal sources cards, email cards, and social share cards are different things and keep their names. Customer copy says “CarlNotes in Claude or ChatGPT” or names the action; it does not introduce MCP view jargon.

An **MCP view route** is one path in the MCP view router: `/search`, `/topic`, `/findings/:topicId`, `/send`,
`/updates`, or `/brew/:topicId`. It runs on a memory history inside the frame and never appears in a host's
address bar. `McpViewShell` is its layout route, and `McpViewLink` moves between routes one hop at most. Paths outside
the router open on the site. A user never sees these paths.

Keep host-cached wire values unchanged: existing `ui://carlnotes/…` URIs and version aliases, the `carlnotes/card` metadata key, resource registration names ending in `-card`, and the `carlnotes-card` host application identity. Rename their constants and helpers, not those compatibility values.


## Layering rules
- Integration = the credential; Source = an input use of it; delivery = an output use of it. Connected once, reused everywhere.
- Ingester = worker code turning a Source into Resources (see ingester-authoring). One composio ingester; toolkit
  variety lives in Source config, not code.
- `packages/contracts/sources.ts` holds both source tables: the default Sources every new Topic starts with, and the
  options the custom picker offers. An entry names the Source kind it saves as and builds its config, so a new Source is
  an entry instead of a kind or a special case. An option is not always a kind: Google News saves as `rss`.
- Topic authority is `topic.owner_id`; the single platform override is an `admin` (`users.role`). Every authority
  **and** entitlement check routes through one `isAllowed(user, capability, resource)` gate — never a scattered `role ===`
  or `tier ===`. The gate resolves a user's **effective role** on a Topic — owner / leader / member / none, the
  strongest grant across the owning and holding teams. Topic access is still "a Subscription path exists."
- Entitlements come from the user's **plan** (`free`/`plus`/`premium`), derived from the active Billing Subscription
  (free = no row) and resolved by the gate.
- Invites are consent-based: the Invite row above holds the kinds and their lifecycle. A topic invite grants topic-page
  view and stands as a pending subscription offer; a team invite offers the join. On invite Topics a subscriber sees
  only Findings from Scans started after their activation; the owner always sees full history. One Scan serves every
  subscriber — the amortization the pricing model assumes.
- A Podcast Episode is rendered output, never an input: an ingested show's episode is a `listen` Resource from the
  `podcast` Source kind, and only a Topic's own rendered audio is a Podcast Episode. Podcast Episode cost counts in the
  billed user's monthly spend beside Scan and chat cost.
- A Resource is raw and global; a Finding is scored and topic-scoped. Don't blur them.
- Personal Source Entry text, derived context, and private annotations stay sender-only, including from Topic owners and admins.
  Personal sources ingesters return public links with null private snippets. Public explanations use only linked-page evidence, and ordinary Topic visibility controls remain available.
- A Scan closes by filtering the Topic to its `max_results` best Findings by relevance; bookmarked Findings are never filtered.
- A Scan traces every Source that did not deliver normally in `scans.problem_sources`: one that fell back to a keyless
  path records its `fallbackMode`, one that failed records its `reason`. A problem is independent of `status` — a Scan
  whose Sources all succeeded, some of them through a fallback, is still `succeeded`.
- A Scan that reaches its closing write records one **source result** per Source in `scans.source_results`: its label
  as of that Scan, its status, its found and kept counts, its ingester's own cost, and its duration. Each Resource is
  credited to the one Source whose copy survived ingest's merge by canonical url, and Sources run oldest first, so the
  same Source wins every time. The **earlier count** is the kept Findings from earlier Scans that no Source returned
  this Scan, which review re-scored. Found counts sum to `found_count`, and kept counts plus the earlier count sum to
  `kept_count`. A stopped Scan, a failed workflow, and a Scan from before the column hold `null`.
- A Scan has **one Budget**, created before ingestion. Every stage charges into it — `ingestion` (the Sources' own
  spend: Exa for `search` and TwitterAPI.io for `x`), `embedding`, `fetch`, `scoringCheap`, `scoringPremium` — so
  `Scan.cost` is that Budget's total and `stage_costs` is its breakdown, and the one spend limit sees everything the
  Scan charges. Never sum a separately tracked ingestion number alongside it.
- A paid ingester reports the dollars it really spent, never zero, and bounds one Scan's spend with its own read limit.
  The Budget is charged once after every Source returns, so a Source cannot consult it mid-run and the limit has to hold
  without one.

## Auth infrastructure is not domain vocabulary
Better Auth manages `users`, `sessions`, `accounts`, `verifications` — identity/access plumbing, the same tier as
`users` itself, never content-domain nouns. `accounts` is sign-in identity only (a password credential or an OAuth grant
used to authenticate) and is never referenced by a Source or a Subscription. The OAuth sign-in providers are Google,
GitHub, and Apple, written "Sign in with Apple" in copy and docs. Apple's web client id is its **Services ID**. The iOS
app's ID tokens name its bundle identifier instead. A user who hides their email with Apple has a **private relay
address** as their email: `@privaterelay.appleid.com` for older sign-ups, and `@private.icloud.com` for new ones from
late 2026. Everywhere else in the app it is an ordinary address, so no code matches on either domain. **Integration**
stays the sole representation of a connected external account used for sourcing or delivery (e.g. Composio-managed
Gmail) — never conflate the two, and never resolve Source/delivery credentials through `accounts`.

## User and visitor name the two states of the person on the page
A **user** is signed in; a **visitor** is not. Identifiers and comments say user where an account is
required — a role, a subscription, a wallet, anything keyed by `user_id` — and visitor only where the
person has no account yet, which is the sign-up and join copy. Never "viewer": it named both states at
once, so `viewerRole` and `viewerUserId` read as if a logged-out person could hold a role. Where the
subject is already unambiguous the qualifier drops entirely: `role`, `userId`. Where it names something else, it says
what: `isTeamLeader`.

A **viewer count** and a **listener count** are the exception. A Topic's viewer count is the distinct people who
opened its page, and a Podcast Episode's listener count the distinct people who played or downloaded it. Both are all
time and count users and visitors alike. A Finding's viewer count counts only the users who opened it. There a viewer
or a listener is one counted member of an audience, never the person on the page, so `viewerCount`, `listenerCount`,
`viewer_counters`, and `addViewer` keep the words. The person who sent a view or a listen is the `RequestSender`.

A profile page and a Team page count viewers the same way: **profile viewers** in `users.profile_viewer_count` and
**team viewers** in `teams.viewer_count`, each with its saved counter in `viewer_counters`. A Topic Post counts its
viewers the same way, in `topic_posts.viewer_count`. Customer copy shows every viewer count as
**Visitors**, which there names the count and never the logged-out state. A Podcast Episode's listener count stays
**Listeners**, and its plays stay **Plays**.

## Café is copy: code says profile
Customer copy calls a person's profile page their **Café**, with the accent, and heads it with the username and then
Café, as in "Evan Café". The word profile never reaches a customer. Every identifier, route, table, comment, AGENTS.md,
and OpenSpec change says **profile**, and the url stays `/profiles/<userId>`. Never `cafe` or `userHomepage` in code.

## On the MCP side, the client is the program and the tool caller resolves to a user or a visitor
The **MCP server** at `/mcp` (and its topic-bound `/mcp/t/<topicId>`) is a second reader over the api's query
layer with the same tool list for everyone. The **client** is the program on the other end (Claude, Cursor,
VS Code), never the person. A **tool caller** is whoever is behind a request before it is resolved, and it resolves
exactly once: an access token the auth server signed for `/mcp` makes it a **user**, anything else makes it a
**visitor**. Past that line identifiers say `user` and `visitor` as everywhere else, and no query runs against a null
user where a visitor branch should run instead. "Add to AI" is the install copy. Better Auth's `oauth_clients`, its
token, consent, and resource tables, and `jwks` are identity plumbing beside `sessions`, never domain nouns. The OAuth
**resource** a token is bound to, `MCP_RESOURCE_URL`, is the `/mcp` url, never a Resource.

## Page is the Topic or the Team a thing lives on
A **page** is exactly one Topic or one Team, and it is what a Note sits on and what a private Chat Turn
is addressed by. The one exception is the **new-topic chat**, a private conversation bound to neither, where Carl makes a
Topic from a Topic Draft. Its Chat Turns store a null Topic and a null Team. `NotePageRef` and `ChatPage` are the same
pair, and `notes` stores it as a nullable
`topic_id` and `team_id` under a check constraint. Never "scope", which already means the chat
attachment's reach, an OAuth grant's permissions, and a Temporal `CancellationScope`. Never "subject",
which already means an email's subject line and the target of a flagged report. A Note's own
`private` / `team` / `public` setting is its **visibility**, never its scope. A **page number** is the other sense of
the word, the position in a paged list, and identifiers say `pageNumber` (from 1), `pageIndex` (from 0), and `pageCount`
so the two never meet in one name. A third sense is the web app's rendered route (`apps/web/src/pages/`, `HomePage`).
The mobile app calls a rendered route a **screen** (`HomeScreen` in `apps/mobile/app/`), the native platform's word, so
"page" on mobile keeps the first two senses only. EAS keeps its own name in identifiers and files (`eas.json`,
`eas-cli`), since Expo Application Services is the vendor's product; prose says EAS Build or EAS Update when the
service matters.

## Follow and subscribe are one concept: follow is the client-facing word, subscribe is the code word
Client-facing copy says **follow**, **follower**, and **following**. Every identifier says **subscribe**,
**subscription**, and **subscriber** — tables, columns, types, functions, routes, and analytics events alike. The
boundary is crossed exactly once, where a string is written for a user to read. Never rename a table toward the copy,
and never let `follow` reach an identifier: a codebase that says both has two names for one thing and no way to tell
which a given `follower_count` means.

## Coffee Talk and brew are branding: code, comments, and agent docs say chat and scan
Client-facing copy, the docs, release notes, the prompt markdown, and the tool descriptions and results Carl repeats say
**Coffee Talk**, **brew**, and **steeping**. Every identifier, comment, AGENTS.md, skill, and OpenSpec change says
**chat**, **scan**, and **loading**.

## Never "surface" for a page or a feature
A **page** is a page. Say `/releases`, the team page, the topic editor, the webhook route: name the
thing. "Surface" says only that a reader might encounter it, which is true of everything and tells the
next reader nothing. It also invites lumping unlike things together, as in a "release notes surface"
that included an inbound webhook nobody looks at. The verb keeps its meaning — an error is surfaced to
a caller — and so does the visual noun, where a card sits on a sunken surface.

## Rules
- Singular entity names in code (`Finding`), plural tables (`findings`).
- New domain nouns get a row in the table above before they appear in code, a table, or a route.
